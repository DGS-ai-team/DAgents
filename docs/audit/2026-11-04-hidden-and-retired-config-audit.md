# Node、Shared、Desktop 与 Manage 配置审计（2026-11-04）

## 结论与范围

审计覆盖 Node 启动 YAML、Node 设置与模型 SQLite、`/v1/settings`、Desktop 设置面板、Agent config snapshot，以及 Manage 的环境变量配置和 Console。判断基于字段定义、持久化、装载/运行时读取和 UI/API 写入链路；本文对其他配置项采用静态检查，不启动生产进程或调用真实 LLM。额度实现按最终代码审阅，Node 全量 `go test ./...` 已通过。

当前有效配置并非一份 YAML：`config.yaml` 负责 Node 的 `listen` 与 Client/Manage 所需的 `local` 引导信息；Node 业务设置落在 `.runtime/node_settings.db`，LLM 档案与加密 key 独立落在 `.runtime/llm_configs.db` 和 `.runtime/.llm_secret_key`；Agent 权限/回合预算在 Agent 的 `config_snapshot`；Manage 部署本身读取 `MANAGE_*` 环境变量。Desktop 的几个“设置”页实际横跨这些不同所有者。

下文优先列出用户可能误判、保存失效、值不可调或凭据落盘的配置。Agent chat turn 由 Desktop `max_tool_calls` 字段和 Node `TurnBudget.MaxToolCalls` 提供单一可配置工具调用上限，默认 64，配置上限 4096。Auto 配置数据模型仍有责任、唤醒间隔和 dreaming 开关等字段，但 `autonomy.Profile` 不含 `max_tool_rounds`；旧字段不属于当前 API 或普通 Agent 的可配置上限，snapshot sanitizer 会删除遗留的 `max_steps`/`max_tool_rounds`。

## Browser service 与 Desktop 本机设置边界

Browser service 有两条配置入口，不能把 Python loader 当成打包产品的唯一来源。**手工运行 Python service** 时，`--config` 或 `DAGENTS_CONFIG` 指向 YAML，`browser-service/dagents_browser/config.py` 读取 `browser` 字段；`DAGENTS_BROWSER_LISTEN` 可指定监听地址，省略字段时使用 Python 默认值（headed=true、timeout=30000ms、output_dir=browser、max_sessions=8、schemes=http/https）（[config.py:10-54](../../browser-service/dagents_browser/config.py)）。**Node 管理的产品 sidecar** 则由 `service_process.go` 从有效 `config.Config` 构造 settings，写入权限为 0600 的临时 JSON/YAML 文件，再以 `--config <temp> --listen <address>` 启动；因此进程环境的 `DAGENTS_CONFIG`/`DAGENTS_BROWSER_LISTEN` 不决定 sidecar 的配置/监听（[service_process.go:128-163, 184-230](../../node/internal/browser/service_process.go)）。Sidecar 当前接收 runtime root、headed、chrome_path、HTTPS errors、timeout、output dir、max sessions、allowed URL schemes。Node Settings UI/API 暴露 headed、chrome_path、HTTPS errors、timeout、output dir、max sessions（[settings.go:135-142, 286-297, 681-699](../../node/internal/setup/settings.go)），其中 `allowed_url_schemes` 虽由有效 Node config 传入，但不在该 DTO/PATCH 中，属于隐藏的高级/配置来源字段；不宜直接建议常规 UI 加项。Browser 页本身管理能力和会话，不直接编辑这些 service 参数（[node/internal/browser/README.md:12-15](../../node/internal/browser/README.md)、[BrowserViewer.vue](../../desktop/tray-tauri/src/ui/components/BrowserViewer.vue)）。

Desktop Rust shell 本身的设置是另一份本机 JSON：`ShellConfig` 只持久化系统通知、Desktop 更新检查开关和间隔（默认通知/更新开启、间隔 6 小时），原子写入 `settings.json`；Node endpoint 固定为 `127.0.0.1:18765`，Browser 地址不在 ShellConfig 中（[config.rs:10-99](../../desktop/tray-tauri/src-tauri/src/config.rs)）。路径按 Windows `%APPDATA%/DAgents/desktop/settings.json`、macOS Application Support、Linux XDG 配置目录选择（[layout.rs:91-125](../../desktop/tray-tauri/src-tauri/src/layout.rs)）。Desktop 设置页确实暴露通知与自动更新项（[DesktopSettings.vue:30-55](../../desktop/tray-tauri/src/views/DesktopSettings.vue)）。当前没有发现被 UI 接受但被 ShellConfig 丢弃的常规字段；Node/Browser endpoint 固定属于产品边界，不是漏掉的用户配置。

## 启动校验与旧 YAML

当前 `config.LoadFile` 会解析 YAML、填默认值、解析 Node ID，并只执行 `ValidateBootstrap`；该校验只覆盖 Node ID、listen 与 local endpoint。完整 `Validate` 在 Node 业务设置与持久设置 overlay 后调用（[config.go:423-445, 539-563](../../shared/config/config.go)、[main.go:46-55](../../node/cmd/dagents-node/main.go)、[node_settings_bootstrap.go:13-48](../../node/internal/store/node_settings_bootstrap.go)）。所以旧 fat YAML 中过期业务值不会仅因为它们未被持久设置采用，就在 bootstrap 阶段按完整业务配置规则拦截启动；YAML 与数据库双来源容易造成“编辑未生效”的权威混乱，但这次静态检查没有证据证明存在“未生效旧值先验证失败”的缺陷。解析错误或 bootstrap 字段错误仍会使启动失败。

## Manage 部署配置与废弃残留

Manage 是单独的服务，部署设置由 `ManageSettings.from_env()` 读取，不由 Desktop Node 设置页持久化（[manage/config.py:25-75](../../manage/config.py)）。部署常用项有 `MANAGE_HOST/PORT`、`MANAGE_DB_PATH`、`MANAGE_BLOB_DIR/BLOB_MAX_BYTES`、`MANAGE_RELEASES_DIR/RELEASE_MAX_BYTES`、bundled release seed 路径/开关、offline grace 与审计内存容量；这些分别被 app、release seed、blob、registry 和 audit 初始化消费（[manage_app.py:52-69, 140-144](../../manage/manage_app.py)、[platform/blob.py:22](../../manage/platform/blob.py)、[releases/routes.py:49-50, 117](../../manage/releases/routes.py)）。Console 的 SettingsView 只有 LLM、发布、案例标签，不是 Manage 服务部署设置（[SettingsView.vue:1-51](../../manage/console/frontend/src/components/SettingsView.vue)）。部署环境变量由运维按 [manage/README.md:101-112](../../manage/README.md) 配置。

有一处字段/消费重复：`ManageSettings.offline_grace_seconds` 在 `from_env()` 填入，但 `manage/registry/store.py` 调用的是 `manage/registry/status.py` 的同名 helper；helper 再次直接读取 `MANAGE_OFFLINE_GRACE_SECONDS`，没有使用传入的 `ManageSettings` 对象（[config.py:41, 71](../../manage/config.py)、[registry/store.py:18, 293](../../manage/registry/store.py)、[registry/status.py:11-20](../../manage/registry/status.py)）。环境变量仍然有效，但 dataclass 字段与 `for_test(offline_grace_seconds=...)` 值对 runtime 不生效；建议将有效值注入 store/status helper，删除重复来源。

`MANAGE_RELEASE_MAX_BYTES=0` 会因为 `or 536_870_912` 被替换为默认 512 MiB（[manage/config.py:68](../../manage/config.py)）；相对而言，`MANAGE_BLOB_MAX_BYTES` 未设置时是 `None`，BlobStore 状态明示不限制（[manage/config.py:64-68](../../manage/config.py)、[platform/blob.py:16-27](../../manage/platform/blob.py)）。这两个上限的 0/未设置语义不同，部署文档应明确。认证变量 `MANAGE_TOKENS`、`MANAGE_SHARED_TOKEN`、`MANAGE_ADMIN_USERNAME/PASSWORD` 在独立 `manage/platform/auth.py` 读取，属于服务运维凭据，不是 Desktop Node 的 Manage Node Token。

## 默认值和 UI/文档落差

- `shared/config.Config.ApplyDefaults` 有通用默认，`ProductNodeSettingsSeed` 又定义首次安装产品默认，后者是 Node 正常新安装的有效来源。不要用 `ApplyDefaults` 的 `skills.max_in_prompt=3` 或 `llm.provider=openai` 推断首次安装行为；产品 seed 使用技能上限 5 与 Mock provider。入口证据：[config.go:451-519](../../shared/config/config.go)、[node_settings.go:181-230](../../node/internal/store/node_settings.go)。
- Hook 工具名单存在真实默认分歧：共享默认 `DefaultToolResultHookTools()` 包含 `terminal_command`（[config.go:322-335](../../shared/config/config.go)）；首次安装 Product seed 写入非空的显式列表，却没有 `terminal_command`（[node_settings.go:221-227](../../node/internal/store/node_settings.go)）；非空配置会整体取代 shared default，不是追加。因此全新设置可能不会对该工具应用结果摘要。建议统一名单并为 seed 结果补覆盖测试。
- `/v1/settings` 的 `restart_required` 目前除 Browser 更新外无条件为 true（[setup_api.go:186-195](../../node/internal/api/setup_api.go)），即便 PATCH 同步了 LLM 运行时、回写了 config 并尝试启动 Manage sidecars。Desktop 把它统一显示为“部分设置需重启后生效”（[useSetupConfig.js:94-99](../../desktop/tray-tauri/src/ui/composables/useSetupConfig.js)）。这是粗粒度提示，容易让用户对热更新设置做不必要重启；建议返回按设置块/运行时结果计算的 restart_required。
- `configPathWritable` 用于 Node 首次从 YAML 种入 LLM 档案后收窄 bootstrap YAML（[server.go:307](../../node/internal/api/server.go)、[setup_api.go:231-254](../../node/internal/api/setup_api.go)）；它不决定设置页的 `ConfigWritable`。设置 API 的可写状态来自 `setupWritable()`，即 Node Settings Store、LLM Config Store 与迁移状态（[setup_api.go:35-40, 188-192](../../node/internal/api/setup_api.go)）。设置页同时展示 config path 与只读状态，文案应继续说明业务设置库可写，避免被理解为 YAML 文件权限。
- 历史设计记录与专门验证清理/拒绝行为的兼容测试夹具仍可能包含 `max_steps`、`max_tool_rounds`、`max_turns`；当前 Agent 设置、Node runtime、OpenAPI 和术语表均以唯一 `max_tool_calls` 限额为准。生产 snapshot sanitizer 会删除旧额度键，旧数据库中遗留的 `child_runs.max_turns` 列不参与当前读写。

## 建议排序

1. 修正用户已观察到的行为：总闸被保存时静默重置为 true；raw-history env 覆盖与 UI 同时呈现；PATCH 的 0 无法清除旧值。
2. 维护废弃配置边界：YAML/SQLite 权威来源说明、`api_key_env` legacy 说明、ChildAgent `turn_count` 的统计语义及唯一 `max_tool_calls` 上限保持同步；不把历史参数重新引入 UI。
3. 修正重复来源和默认差异：将 Manage offline grace 值注入实际消费点；统一 Hook tool list；细化 `restart_required`。
4. 凭据静态存储：先确认威胁模型，再决定 Node token/Webhook key 是否需要静态加密及兼容迁移；无需隐藏当前 UI 管理入口。

## 扫查范围与边界

读过 `shared/config` 的 Config/default/validation/path helpers、Node Settings/LLM Stores 与 migration、`node/internal/setup` GET/PATCH、相关 API/runtime consumer、Desktop Settings panels/composables/Agent form 与 Rust ShellConfig/path、Manage env config/auth/blob/release/status/runtime、Browser service config、以及现有配置参考文档。最终实现仅以 `max_tool_calls` 作为工具调用预算门槛，ChildAgent `max_turns` 不再作为配置或执行限制；旧 snapshot 键会被 sanitizer 删除，旧数据库中的 `child_runs.max_turns` 列可惰性保留。该额度改动已通过 Node 全量 `go test ./...`；本文其余配置项仍是静态链路审计，未逐项运行专项测试。未穷举每个工具的参数、MCP Server 与 Linux channel 各自表结构，也未审查所有 `localStorage` UX 偏好；它们是独立子系统，不据此宣称整个仓库没有其他配置项。未逐项检查操作系统安装器/打包环境变量的默认值；可针对证实的覆盖层和零值语义补专项集成测试。
