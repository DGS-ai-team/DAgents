## 1. 为什么做这个项目

### 1.1 技术路线：为什么是 Agent

AI 是目前少数能**大幅度提升生产力**的工具之一。若只停留在纯 Chat、RAG 或固定 Workflow，能力边界往往清晰可预期：问答、检索、按剧本执行。  
**叠加完备 harness 的 Agent** 则多出一整层——模型在约束下**自主选工具、多步推理、与人协作（HITL）、持久会话**，能处理「先查再改、审批后再跑、跨文件跨命令」这类开放式任务。  
这是当前**最贴近「个人助手」**的一条技术路线：不是替人写一段答案，而是在人的策略与审批下，替人**完成一段工作**。

DAgents 的 harness 即这一层：`turn loop`、内置工具、策略审批、会话与压缩、trigger、跨 Agent 协作等（详见 [04-能力与策略](./04-能力与策略.md)）。

### 1.2 市面已有优秀产品，为什么还要自己做

常见 Agent 产品（通用助手、IDE Agent、垂类 Copilot 等）在各自场景里已经很强，但在**企业落地**时仍常遇到三类缺口——这也是 DAgents 存在的理由：

| 动机 | 说明 | 在 DAgents 中的回应 |
|------|------|---------------------|
| **场景与习惯** | 企业业务背景、流程、合规习惯各不相同；通用 Agent 偏「人人可用」，垂类产品也未必贴合**本企业**的术语、审批链、工具链与分工 | 开源可改、可配：`policy/`、skills、`custom.md`、Agent Card、Manage 分组；可按组织定制而非黑盒订阅 |
| **基础设施现实** | 市面产品多假设较新的服务器与云环境；企业大量**存量、老旧**设施仍承载核心业务 | Agent **下沉到目标机**（Go Node）；人机用 **Web UI**（本机或隧道）；Manage 可另机部署，Node **仅需出站** |
| **理解核心技术** | Agent 的难点在 harness（队列、turn、HITL、工具策略、上下文、协作），只使用产品很难触及实现；**真正上手做**，才能理解设计取舍与边界 | 本仓库即可运行的参考实现 + [项目手册](./README.md)；读源码路径见 [02-Agent-Node-核心](./02-Agent-Node-核心.md) |

简言之：**不是要再造一个「更大号的 ChatGPT」**，而是要做一种可部署、可改造、可跟读的 **Agent 运行时**——既服务「老旧环境 + 企业习惯」的落地，也服务「把 Agent 技术吃透」这一目标。

### 1.3 是什么

**DAgents** 是面向「**工具调用 + 人工审批（HITL）+ 会话持久化**」的**本地优先 Agent 控制台**：

- **思考与执行**在 **Go Agent Node**（`node/`）：多 Agent 实例、LLM turn loop、内置工具、SQLite、skills、压缩、trigger。  
- **人机交互**默认在 **内嵌 Web UI**（`/ui/`）；桌面托盘可选。  
- **跨 Node 协作与运维**在 **Manage**（`manage/`）：Registry、**Workgroup**、Vue Console。  

精简二进制 `dagents-client` 用于 probe / update / version 等运维命令。

### 1.4 非目标

| 非目标 | 说明 |
|--------|------|
| **浏览器直连 Manage 当对话入口** | 对话走 Node `/ui/` 或工作组 UI；Console 是运维面 |
| **Node 直连其他 Node 驱动成员** | 工作组工具命令经 Manage 编排与下发 |
| **开箱 SaaS** | 需自行配置 LLM、策略、部署 |
| **独立沙箱进程** | 边界靠工具组、审批策略与工作区路径 |

### 1.5 架构选择：为什么 Agent 本体用 Go

企业大量**存量、老旧**设施仍承载核心业务，却往往跑不了「推理 + 工具 + UI」绑在同一高版本 Python 进程里的方案。DAgents 因此把：

1. **Agent 本体做成 Go 二进制**——工具与 turn 留在**目标机**上执行。  
2. **人机交互做成 Web UI**——同机浏览器打开 `/ui/`；也可无头部署 Node，从他机经 VPN/隧道访问。

这样 AD、PowerShell、本机 cron、仅本机可访问的配置与 socket 仍留在 Agent 可达范围内。

#### 部署选型

| 策略 | 适用场景 | 部署方式 |
|------|----------|----------|
| **A · 同机 Web UI** | 本机有浏览器或可隧道打开 | 目标机跑 **Go Node**；浏览器打开 `/ui/` |
| **B · 无头 Node** | 目标机无桌面 | Node `listen` 绑内网；从办公机浏览器经 VPN/隧道访问 `/ui/` |
| **C · Manage 另机** | 注册与工作组中枢 | Manage 跑较新 Linux/容器；Node **仅需出站** |

#### 按环境速查

| 环境 | 主要限制 | 推荐策略 |
|------|----------|----------|
| RHEL 6 / CentOS 6 | glibc 旧 | **A/B** Node 二进制 + 远程浏览器 |
| RHEL 7 / 老 Windows | 终端弱 | **A** Web UI；或 **B** 隧道 |
| 较新 Linux / WSL / Win10+ | 齐全 | 同机 Node + `/ui/` |
| 运维 / 注册中心机 | 适合容器 | **Manage**（可选） |

详见 [03-API与Client](./03-API与Client.md)、[06-运维与案例](./06-运维与案例.md)。

## 2. 组件模型

### 2.1 总览（现行）

```text
┌──────────────────┐   HTTP/SSE    ┌──────────────────┐
│  Web UI /ui/     │ ────────────► │   Agent Node     │  Go · 多 Agent
│  （本机浏览器）    │ ◄──────────── │ turn·工具·SQLite  │
└──────────────────┘               └────────┬─────────┘
                                            │ manage + workgroup
                                            ▼
                                   ┌──────────────────┐
                                   │     Manage       │  Python
                                   │ Registry·Workgroup│
                                   │ Console /console/ │
                                   └────────┬─────────┘
                                            │ WS / outbox
                                   ┌────────┴─────────┐
                                   │ 其他 Agent Node   │  Member Home
                                   └──────────────────┘
```

默认同机打开本机 `/ui/`。跨机协作：多 Node 注册同一 Manage，成员工具在 Home Node 执行。见 [07-Workgroup协作](./07-Workgroup协作.md)。

### 2.1.1 部署拓扑

| 拓扑 | Node | 人机 | 配置要点 |
|------|------|------|----------|
| **同机（默认）** | `listen: 127.0.0.1:18765` | 浏览器 `/ui/` | 无需额外前端进程 |
| **Node 无头** | 仅跑 Node | 从他机浏览器或隧道访问 `/ui/` | 注意鉴权与防火墙 |

对话路径始终是 **人机 → Node**；Manage 仅 Node 出站（注册 / Workgroup）。

### 2.2 职责与硬边界

| 组件 | 语言 | 职责 | **禁止** |
|------|------|------|----------|
| **Web UI / 运维 CLI** | Vue / Go | 发消息、收 SSE、HITL resume、会话 UI；`dagents-client` 做 probe/update | 直连 Manage 跑对话；在浏览器侧执行工具 |
| **Agent Node** | Go | LLM、turn、工具、持久化、向 Manage 注册 | 直连其他 Node 驱动成员；跑 Manage UI |
| **Manage** | Python | 注册、发现、Workgroup 编排、审计、Console | 跑本机 Agent turn loop；代理本机对话消息 |

> **连接范围**：浏览器 / CLI **只**连 **Agent Node**（默认同机 `127.0.0.1`；远程访问时指向目标机 Node）。**不**把 Manage 当对话后端。

### 2.3 身份与端口

| 规则 | 说明 |
|------|------|
| **一端口 = 一 `agent_id`** | 每 Node 进程监听一个地址，身份即配置中的 `agent_id` |
| **临时子 Agent** | Node **内部** session；共用进程、FS 根、端口；**不**单独暴露 HTTP |
| **`expose_to_peers`** | 控制是否可作为 A2A **被调目标**；**无论是否暴露，均须注册 Manage** |
| **同机多 Node** | 多进程、多端口、多 `agent_id`；各配独立 config |

### 2.4 典型数据流

**本地会话**（详见 [03-API与Client](./03-API与Client.md)）：

```text
Client → POST /v1/messages → Node 入队 → turn loop → SSE → Client
HITL：SSE hitl_required → Client 按 item 分步 POST resume → 继续 turn
（A2A 中继仍用 approval_required / user_information_required）
```

**A2A**（详见 [05-Manage与A2A](./05-Manage与A2A.md)）：

```text
**协作（工作组）**：

```text
Agent 经 Manage 工作组 Dialer 与成员协作
禁止：Agent A → Agent B 直连派活（跨机请用 Workgroup）
```

**Node 启动**：

```text
读 config → api.NewServer 装配 → Listen
并行：registrar 注册/心跳（可选 workgroup dialer）
```

## 4. 架构决策（ADR）

1. **LLM / turn loop 在 Agent Node（Go）**  
2. **一进程多 Agent**（`node_id` + 多个 `agent_id`）；子 Agent 不暴露端口  
3. **Manage**：注册 + 心跳 + **Workgroup** + Console  
4. **人机默认 Web UI**（`/ui/`）  
5. **跨机协作经 Workgroup**（成员命令经 Manage，不 Node 互直连）  
6. **工具边界**：工具组 + 审批策略 + 工作区路径（无独立沙箱进程）
