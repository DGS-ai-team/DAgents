## 1. 为什么做这个项目

### 1.1 技术路线：为什么是 Agent

AI 是目前少数能**大幅度提升生产力**的工具之一。若只停留在纯 Chat、RAG 或固定 Workflow，能力边界往往清晰可预期：问答、检索、按剧本执行。  
**叠加完备 harness 的 Agent** 则多出一整层——模型在约束下**自主选工具、多步推理、与人协作（HITL）、持久会话**，能处理「先查再改、审批后再跑、跨文件跨命令」这类开放式任务。  
这是当前**最贴近「个人助手」**的一条技术路线：不是替人写一段答案，而是在人的策略与审批下，替人**完成一段工作**。

DAgents 的 harness 即这一层：`turn loop`、内置工具、策略审批、会话与压缩、trigger、跨 Agent 协作等（详见 [04-能力与策略](./04-能力与策略.md)）。

### 1.2 市面已有优秀产品，为什么还要自己做

常见 Agent 产品（通用助手、IDE Agent、垂类 Copilot 等）在各自场景里已经很强，但在**企业落地**时仍常遇到三类缺口——这也是 DAgents 存在的理由：

| 动机 | 说明 | 在 DAgents 中的回应 |
|------|------|---------------------|
| **场景与习惯** | 企业业务背景、流程、合规习惯各不相同；通用 Agent 偏「人人可用」，垂类产品也未必贴合**本企业**的术语、审批链、工具链与分工 | 开源可改、可配：`policy/`、skills、`custom.md`、Agent Card、Manage 分组；可按组织定制而非黑盒订阅 |
| **基础设施现实** | 市面产品多假设较新的服务器、OS、终端与云环境；企业大量**存量、老旧**设施仍承载核心业务，不应因 AI 潮流被整体「跳过」 | Agent **下沉到目标机**（Go Node）；终端差时用 **同机 plain REPL**，或 **Client / Node 前后端分离**——在较新机器跑 Textual / Go full TUI，远程连目标机上的 Node；Manage 部署在较新环境，Node **仅需出站** |
| **理解核心技术** | Agent 的难点在 harness（队列、turn、HITL、工具策略、上下文、协作），只使用产品很难触及实现；**真正上手做**，才能理解设计取舍与边界 | 本仓库即可运行的参考实现 + [项目手册](./README.md)；读源码路径见 [02-Agent-Node-核心](./02-Agent-Node-核心.md) |

简言之：**不是要再造一个「更大号的 ChatGPT」**，而是要做一种可部署、可改造、可跟读的 **Agent 运行时**——既服务「老旧环境 + 企业习惯」的落地，也服务「把 Agent 技术吃透」这一目标。

### 1.3 是什么

**DAgents** 是面向「**工具调用 + 人工审批（HITL）+ 会话持久化**」的**本地 Agent 运行时**：

- **思考与执行**在 **Go Agent Node**（`node/`）：LLM turn loop、内置工具、SQLite 会话、skills、压缩、trigger。  
- **人机交互**在 **Client**（`app/cli/` Python Textual 或 `client/` Go bubbletea/REPL）。  
- **跨 Agent 协作与运维**在 **Manage**（`manage/`）：Registry、A2A Task、Vue Console。

### 1.4 非目标

| 非目标 | 说明 |
|--------|------|
| **Client 连 Manage** | Client **只**连本机 Node |
| **Node 直连 peer** | A2A **必须**经 Manage |
| **远程多 Agent 统一 Web 入口** | Manage Console；Node `/ui/` 仅连本机 Node |
| **开箱 SaaS** | 需自行配置 LLM、策略、部署 |

### 1.5 架构选择：为什么 Agent 本体用 Go

§1.2 中「老旧设施」不仅是口号，也直接驱动了 v2 架构收敛：

原 Python 单体把 **推理、工具、TUI 绑在同一 Python 进程**里，受限于 **Python 3.11+、textual、目标机 glibc**。大量老旧服务器（RHEL 6/7、Windows Server 2012）上有不可替代的本地 shell/文件/业务，却无法稳定跑这一套。

v2 重设计做两件事：

1. **Agent 本体下沉 Go**（静态/近静态二进制）——工具与 turn 留在**目标机**上执行。  
2. **人机交互拆成独立 Client**——与 Node 仅通过 HTTP/SSE 协作，**不必与 Agent 同进程、甚至不必同机**。

这样 AD、PowerShell、遗留 cron、仅本机可访问的配置与 socket 仍留在 Agent 可达范围内；交互体验则不必被老 conhost / 老 SSH 终端拖死。

#### 老旧环境下的两种部署策略

| 策略 | 适用场景 | 部署方式 |
|------|----------|----------|
| **A · 同机极简** | 必须 SSH 登在目标机上操作；终端能力弱但可接受行模式 | 目标机跑 **Go Node + `dagents-client tui --plain`**（或 Go full TUI）；同一份 config，`listen` 与 `local.endpoint` 均指向本机 |
| **B · 前后端分离** | 目标机终端交互差，但旁边有 WSL、跳板机、办公 Linux 等**较新环境** | **后端**：老旧目标机跑 **Go Node**（可无头，仅监听 HTTP/SSE）；**前端**：较新机器跑 **Python Textual** 或 **Go full TUI**，`local.endpoint` 指向目标机 Node 地址；工具仍在目标机本地执行 |

策略 B 示意：

```text
  ┌─────────────────────┐         HTTP/SSE          ┌─────────────────────┐
  │ 较新机器（前端）      │ ───────────────────────► │ 老旧目标机（后端）    │
  │ dagents chat        │   local.endpoint 指向    │ dagents-node        │
  │ 或 dagents-client   │   目标机 IP:port         │ bash / 文件 / 遗留 CLI │
  │ tui（全屏体验）      │ ◄─────────────────────── │ SQLite · turn loop   │
  └─────────────────────┘                         └─────────────────────┘
```

要点：

- **能力在后端**：shell、FS、审批策略、会话库都在 Node 所在机器，不是「远程桌面里再跑一套 Agent」。  
- **体验在前端**：Textual、bubbletea 全屏、现代终端特性放在**能跑好的机器**上。  
- **默认同包不等于必须同机**：Release 里 Node 与 Client 绑在一起是为了简化安装；架构上二者本就是分离进程，跨机只需对齐 `listen` / `local.endpoint`（生产环境建议内网 + 鉴权或 SSH 隧道，见 [03-API与Client](./03-API与Client.md) §1）。  
- **Manage 仍可选第三处**：注册与 A2A 控制面跑在较新 Linux/容器，Node **仅需出站**连 Manage。

#### 按环境选型（速查）

| 环境 | 主要限制 | 推荐策略 |
|------|----------|----------|
| RHEL 6 / CentOS 6 | glibc 2.12，现代 Python 难部署 | **A** 同机 Node + plain；或 **B** Node 在 RHEL6、Client 在跳板机 |
| RHEL 7 / 老 Windows SSH | 终端能力弱 | **A** plain / Go REPL；或 **B** 办公机 Textual 连远程 Node |
| 较新 Linux / WSL | 终端与依赖齐全 | 同机 **`dagents chat`** 或 Go full TUI（策略 A 的舒适版） |
| 运维 / 注册中心机 | 适合容器与 FastAPI | **Manage**（不要求部署在 RHEL 6） |

详见 [附录/重大设计变更实录](./附录/重大设计变更实录.md) 背景节、[03-API与Client](./03-API与Client.md) §3、[06-运维与案例](./06-运维与案例.md) §3。

## 2. 三组件模型

### 2.1 总览

默认**同机**部署（Client 读 `local.endpoint` → 本机 Node），但架构上 **Client 与 Node 始终是两个进程**，可拆到不同机器（见 §1.5 策略 B）。

```text
┌─────────────┐   HTTP/SSE    ┌──────────────────┐
│   Client    │ ────────────► │   Agent Node     │  Go · Agent 本体
│ 双 TUI 任选  │ ◄──────────── │ turn·工具·SQLite  │
└─────────────┘  本机或远程    └────────┬─────────┘
                                       │ 出站：注册 / 心跳 / inbox / 审计
                                       ▼
                              ┌──────────────────┐
                              │     Manage       │  Python · 控制面
                              │ Registry · A2A   │
                              └──────────────────┘
                                       ▲
                                       │ 同上（A2A 不经 peer 直连）
                              ┌────────┴─────────┐
                              │ 其他 Agent Node   │
                              └──────────────────┘
```

### 2.1.1 Client ↔ Node 部署拓扑

| 拓扑 | Node | Client | 配置要点 |
|------|------|--------|----------|
| **同机（默认）** | `listen: 127.0.0.1:18765` | 同机 TUI | `local.endpoint: http://127.0.0.1:18765` |
| **前后端分离** | 目标机 `listen` 监听可达地址 | 较新机器跑 TUI | Client 的 `local.endpoint` 指向目标机；Node 上工具仍在本地执行 |
| **Node 无头** | 目标机仅跑 Node | 运维从跳板机 / 办公机连入 | 与上一行相同；目标机可不装 Python Textual |

Client **不**连 Manage；跨机场景下仍是 **Client → Node** 一条会话路径，Manage 仅 Node 出站使用。

### 2.2 职责与硬边界

| 组件 | 语言 | 职责 | **禁止** |
|------|------|------|----------|
| **Client** | Python / Go | 发消息、收 SSE、HITL resume、会话 UI | 连 Manage；执行工具 |
| **Agent Node** | Go | LLM、turn、工具、持久化、向 Manage 注册 | 直连其他 Node；跑 Manage UI |

> **Client 连接范围**：Client **只**连 **Agent Node**（默认同机 `127.0.0.1`；前后端分离时为 `local.endpoint` 指向的目标机 Node）。**不**连 Manage。
| **Manage** | Python | 注册、发现、A2A 中继、审计、Console | 跑 turn loop；代理 Client 消息 |

### 2.3 身份与端口

| 规则 | 说明 |
|------|------|
| **一端口 = 一 `agent_id`** | 每 Node 进程监听一个地址，身份即配置中的 `agent_id` |
| **临时子 Agent** | Node **内部** session；共用进程、FS 根、端口；**不**单独暴露 HTTP |
| **`expose_to_peers`** | 控制是否可作为 A2A **被调目标**；**无论是否暴露，均须注册 Manage** |
| **同机多 Node** | 多进程、多端口、多 `agent_id`；各配独立 config |

**本地会话**（详见 [03-API与Client](./03-API与Client.md)）：

Client → POST /v1/messages → Node 入队 → turn loop → SSE → Client
HITL：SSE hitl_required → Client 按 item 分步 POST resume → 继续 turn
（A2A 中继仍用 approval_required / user_information_required）
```

**A2A**（详见 [05-Manage与A2A](./05-Manage与A2A.md)）：

```text
**协作（工作组）**：

```text

## 4. 架构决策（ADR）

1. **LLM / turn loop 在 Agent Node（Go）**  
2. **一端口一 `agent_id`**；子 Agent 不暴露端口  
3. **Manage**：注册 + 心跳 + 工作组 + 运维 Console；Client 不访问 Manage  
4. **Client 只连本地 Node**；同包发布、同 config  
5. **跨机协作经 Manage 工作组**；禁止 Node 直连（旧 A2A inbox 已拆除）  
6. **Python 仓库保留 Manage + TUI**；Agent 执行仅在 Go Node  

架构级优化见 [附录/重大设计变更实录](./附录/重大设计变更实录.md)。
