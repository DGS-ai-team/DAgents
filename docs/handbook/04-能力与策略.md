# 04 · 能力与策略

本章是能力域的兼容入口。工具字段以 `node/internal/tools/REFERENCE.md` 和 [内置工具参考](附录/内置工具参考.md) 为准；跨组件生命周期见 [架构](../architecture.md)。

## 1. 能力如何进入一次模型请求

```text
Agent 配置
  → enabled tool groups + policy + hooks
  → tools.Registry.Definitions()
  → provider API 的 tools 参数
  → tool router
  → auto / HITL / deny / async task
  → result contract + history + SSE
```

工具 Schema 通过模型 API 的 `tools` 字段传递，不应重复拼进 system message。工具描述要说明用途、参数约束、结果字段、空输出/截断、耗时和审批影响。

常用工具域：

| 域 | 代表能力 |
|---|---|
| 文件 | `read_file`、`write_file`、`search_replace`、`glob_files`、`grep_file`、`grep_files`、`read_image`、`show_image` |
| Shell | `bash_run` |
| Terminal | `terminal_open`、`terminal_input`、`terminal_read`、`terminal_list`、`terminal_config_list`、文件传输 |
| Browser | `browser_run_task`、`browser_task_status`、`browser_task_cancel` |
| Skills | `list_available_skills`、`load_skills`、`unload_skills`、`clear_skills` |
| 协作/自动化 | 临时 Agent、Triggers、MCP、WeCom、`remember` |
| 人机交互 | `ask_user_information` |

## 2. Policy、Hook 与审批

工具是否能执行由 Agent 的工具组、Node policy 和 Hook 共同决定：

| 决策 | 行为 |
|---|---|
| `auto` | 直接执行，并返回结构化结果 |
| `approval` | 生成 HITL item，等待用户逐项或批量决议 |
| `deny` | 不执行，返回 `policy_denied` |
| `async task` | 仅对工具自身定义的异步任务建立 job，状态和结果异步回灌 |

Node 的策略文件位于 runtime `policy/`，初始种子在 `packaging/runtime/policy/`。`tool.before_each` / `tool.after_each` 可补充重复调用、Agent 自有文件等信任链，但 Hook 不能绕过 `always` 审批或扩大工具权限。

工具结果必须依靠 `status`、`error`、`exit_code`、`output_empty`、`job_id` 等事实判断；不能用空正文、`ERROR:` 前缀或本地化文案猜测执行结果。

## 3. Skills 的发现与加载

Skills 分为目录元数据和正文两个阶段：

1. 目录元数据在新会话或上下文重建时写入 system prompt，帮助模型决定是否加载；
2. 模型调用 `load_skills` 后，正文进入当前 session 的 `loadedSkills`；
3. 正文通过独立的 ContextInjection/context message 进入后续模型请求，不重复拼到 system prompt；
4. 正在进行的模型请求不被中途改写；显式加载/卸载在下一个模型 Step 边界生效；
5. 磁盘目录变化不改写当前 system prompt；模型可通过 `list_available_skills` 获取最新列表，新的元数据快照在下一次 human Turn 或上下文重建时生效。

`list_available_skills` 只负责发现，不加载正文、不修改 loaded 状态，也不会改写当前 system prompt。system prompt 中的元数据来自 context boundary 固定的目录快照；`skills.max_in_prompt` 约束同时启用的技能数量。正文仅在 `load_skills` 后作为会话上下文生效。大正文应拆分或精简，避免长期占用上下文。

## 4. Terminal 与远程执行

Terminal 是有生命周期的交互会话：先 `terminal_open`，再通过 `terminal_input` 写入、`terminal_read` 读取，并用 WebSocket/游标观察输出。Node 支持本机、WSL、PowerShell/CMD 和 Linux SSH 目标；每个终端的类型、目标和用户必须由配置/快照明确返回。

Shell `bash_run` 是一次性、同步的命令执行能力，与交互 Terminal 分开；超时直接失败，不转后台。只有 `browser_run_task(wait=false)` 等明确声明异步语义的工具才建立任务并异步回灌结果。远程 Linux 通道还需 SSH 主机密钥校验和 policy/HITL。不要把离开 UI 页面理解为终止终端，权威 close、显式 terminate 或 idle 超时才会结束它。

## 5. Browser 与 MCP

Browser 任务通过 `browser_run_task` 交给独立 sidecar；Node 保留任务、审批和结果回灌边界，状态查询和取消可在 Node/sidecar 重启后恢复。详细实现见 [browser-remote-service-mode-a.md](../design/browser-remote-service-mode-a.md)。

MCP 服务由 Node 管理连接、凭据、工具目录和 Agent allowlist；服务状态是 Node 级状态，工具暴露仍按 Agent 策略过滤。Manage 不接收 MCP secret。

## 6. Triggers、子 Agent 与记忆

- Triggers 写入 runtime `triggers/`，触发后以队列消息进入 session，不能绕过 policy/HITL。
- 临时子 Agent 是同一 Node 内独立 runtime，有独立 history/queue 和受限工具注册表；完成后通过父 session relay 结果。
- `remember` 写入 Agent 记忆侧车；下次请求以明确来源的 ContextInjection 读取，不应伪装成用户原话。

## 7. 上下文与缓存约束

- system prompt、tools schema、history 和 ContextInjection 在请求前组成快照；同一 Turn 的多个 Step 使用一致边界。
- 工具清单或 skills 清单变化可能造成模型前缀缓存失效，这是能力正确性成本，应记录 revision 而不是偷偷复用旧 Schema。
- skills 正文变化受加载 Hook 和 Step 边界保护；不引入每轮动态尾部，避免割裂对话连续性。
- 压缩只在父 session 的安全边界运行，并尽量复用稳定前缀；压缩后的摘要仍要标明来源和生效边界。
