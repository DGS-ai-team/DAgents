# Agent 质量与效果提升方案

本文规划 DAgents 在 Turn / Step 运行时重构完成后的下一阶段工作，目标是提升 Agent 的端到端任务完成质量、工具使用正确性、失败恢复能力和结果可信度。

本文是实施方案，不代表所有内容已经落地。后续每个阶段都应通过评测基线和回归测试确认收益后再进入下一阶段。

## 1. 目标与原则

### 1.1 质量目标

- 正确理解用户目标、约束和完成条件。
- 选择合适的工具，并正确填写工具参数。
- 能够检查工具结果，而不是仅依据工具调用成功推断任务成功。
- 工具失败、返回空结果或结果不确定时，能够诊断、重试或更换方法。
- 最终回答区分已观察事实、推断结果和未知信息。
- 不在缺少证据时声称任务已经完成。
- 在需要等待异步任务、用户确认或外部事实时保持正确的等待状态。
- 在安全、延迟和成本可接受的前提下，提高复杂任务的完成率。

### 1.2 设计原则

1. **先测量，再调优**：没有端到端评测基线，不进行只凭主观感受的提示词调参。
2. **运行时事实权威**：模型负责理解和决策，Runtime 负责记录状态和工具事实，Verifier 负责判断完成证据。
3. **稳定上下文优先**：不引入动态尾部，不通过不断修改 system prompt 传递执行状态。
4. **质量优先、成本可观测**：工具清单、Skills 清单和 Skills 正文的真实语义变化造成缓存失效是可接受成本，但必须记录和评估。
5. **集中式结构而非补丁式条件**：将任务契约、工具执行计划和验证结果放入统一运行时结构，避免在多个分支中重复添加特殊判断。
6. **权威事件驱动**：前端、日志和后续恢复逻辑只依赖明确的生命周期事件，不根据模糊的文本或 UI 状态推断任务阶段。

## 2. 当前基础与主要缺口

### 2.1 已具备的基础

当前 Turn / Step 运行时已经提供了后续质量提升所需的主要基础：

- Turn、Step、ModelAttempt、ToolBatch 和 ToolExecution 已有统一生命周期。
- 当前 Turn 固定 system prompt 和 tools snapshot，避免工具循环期间上下文定义漂移。
- 模型请求重试、读取型工具重试、HITL、Turn 取消和异步回调已经具备运行时承载能力。
- 大型工具结果可以溢出到文件，并在上下文中保留摘要和完整结果指针。
- Hook 覆盖 prompt、模型调用、工具调用、HITL、Turn 完成和错误等阶段。
- 生命周期事件可以作为前端状态和恢复流程的事实来源。

### 2.2 影响效果最大的缺口

1. 系统提示词尚未明确规定任务完成标准、结果验证、失败恢复和事实等级。
2. 工具 Schema 和工具结果缺少统一的成功、失败、空结果和可验证语义。
3. 多工具自动并行主要依据模型批次，缺少资源冲突和副作用分类。
4. 工具全部执行完并不等于任务完成，当前需要更明确的后置验证和完成判定。
5. 缺少可重复的 Agent 端到端质量评测框架。
6. Skills 的执行契约和质量检查不足；长期记忆的相关性、来源和置信度仍可提升。

## 3. 目标运行时结构

后续质量能力围绕以下内部结构组织：

```text
TaskContract
    ↓
StepDecision
    ↓
ToolExecutionPlan
    ↓
VerificationResult
    ↓
TurnCompletion
```

### 3.1 TaskContract

表示当前 Turn 要完成的目标和约束，建议包含：

- 用户目标。
- 明确约束。
- 完成条件。
- 风险等级。
- 验证模式。
- 未解决事项。

第一阶段不要求额外增加一次模型调用来生成结构化计划。可以先由 Runtime 保存用户输入、工具事实和配置推导出的内部状态；是否需要模型产生结构化计划，后续以评测数据决定。

### 3.2 StepDecision

统一描述当前 Step 完成后的下一步：

```text
ContinueForToolResults
WaitForHITL
WaitForAsync
NeedVerification
Complete
Fail
```

它用于替代分散在 Orchestrator、Tool Router 和 Session Runtime 中的隐含分支。

### 3.3 ToolExecutionPlan

表示模型返回的工具调用经过 Runtime 分析后的执行计划，至少应包含：

- 原始 Tool Call 顺序。
- 工具能力分类。
- 并行组和串行组。
- 资源或目标冲突。
- 是否需要后置验证。
- 当前批次的取消和超时策略。

### 3.4 VerificationResult

表示任务或工具结果的验证事实：

```text
passed | failed | partial | unverified
```

同时记录证据、失败原因和未解决事项。Verifier 不能把模型的自然语言陈述当成证据，证据必须来自工具结果、异步回调、明确的系统状态或配置的后置检查。

## 4. 分阶段实施计划

### 阶段 0：建立质量评测基线

这是所有行为修改前的前置阶段。

首批准备 12～20 个黄金场景，覆盖：

- 普通问答和复杂指令理解。
- 文件搜索、读取、修改和修改后验证。
- bash/local terminal 操作。
- `linux_exec` 远程命令和空输出命令。
- 多工具连续调用。
- 独立只读工具并行。
- 读写冲突和有顺序依赖的工具调用。
- 工具失败后的重试和换方案。
- 异步任务回调。
- Turn 取消、HITL 暂停和恢复。
- Skills 加载和 Skills 指令冲突。
- 长上下文压缩和记忆读取。

每个场景记录：

- 端到端任务是否成功。
- 工具名称、参数和调用顺序是否正确。
- 是否检查了工具结果。
- 是否出现无证据的成功声明。
- Step 数量、工具调用数量、重试次数和耗时。
- 错误恢复是否成功。
- HITL、异步等待和取消是否正确。
- token、成本和上下文缓存命中情况。

评测分为两层：

- Fake LLM / Fake Tool 的确定性回归测试，用于验证运行时行为。
- 真实模型的周期性 A/B 测试，用于验证提示词和模型策略的实际收益。

### 阶段 1：稳定 System Prompt 与工具契约

这是预计收益最高、风险最低的行为改进阶段。

#### 稳定 System Prompt 增加任务执行契约

在稳定 system prompt 中增加通用规则：

- 先理解目标、约束和完成条件。
- 多步骤任务形成内部执行计划。
- 选择最少但足够的工具。
- 每次工具调用后检查结果。
- 遇到失败、空结果或不确定结果时诊断、重试或更换方法。
- 没有证据时不能声称成功。
- 区分观察事实、推断结果和未知信息。
- 对安全的只读操作不要过度询问。
- 只有在缺少关键信息、存在破坏性操作或权限不明确时才询问用户。
- 最终回答说明结果、关键证据、失败步骤和未完成事项。

不把当前任务计划、工具结果摘要或实时进度追加到动态 system prompt 中，以免破坏上下文连续性。

#### 修正子 Agent 的交互策略

子 Agent 不应默认“多向用户确认”。应改为：只有在关键信息缺失、权限或安全边界不明确、或者无法继续时才请求确认。

#### 统一工具 Schema

工具描述统一说明：

- 用途和适用场景。
- 参数约束。
- 是否有副作用。
- 成功判定。
- 失败表现。
- 是否允许重试。
- 输出字段含义。
- 是否需要后续验证。

`bash_run` 和 `linux_exec` 使用统一的结果语义，至少包括：

```text
exit_code
stdout
stderr
target
cwd
duration
truncated
job_id
termination_status
```

即使 stdout 为空，也必须明确表达 `stdout_bytes = 0`，避免模型把“无输出”误判为工具没有执行。

### 阶段 2：工具能力分类、调度与验证

#### 工具能力分类

在 Registry 内部增加工具能力元数据：

```text
ReadOnly
Idempotent
ParallelSafe
Mutating
RequiresOrder
LongRunning
NeedsVerification
RemoteTarget
```

#### 安全并行调度

- 多个无冲突的只读工具可以并行。
- 写入、删除和配置变更默认串行。
- 可能操作同一资源的工具必须串行。
- 远程命令、后台任务和交互式任务单独处理。
- 模型一次返回多个 Tool Call 时，Runtime 先分析依赖，不能盲目并行。
- 实时事件可以按完成顺序发送，但模型历史仍按原始调用顺序写入。

#### 后置验证

为工具和 Agent 增加可选验证模式：

```text
off     不主动验证
safe    验证低成本、低风险操作
strict  对远程、写入、删除和配置变更强制验证
```

典型验证包括：

- 文件写入后检查文件是否存在或内容是否符合预期。
- 命令执行后检查退出码和关键输出。
- Linux 远程操作后检查目标机的实际状态。
- 异步任务以回调或最终状态作为完成依据，而不是以提交成功作为完成依据。

没有验证证据时，最终状态应为 `unverified` 或 `partial`，不能静默转换成成功。

### 阶段 3：补强 Turn / Step 语义

保留当前定义：

- Turn：一次用户请求到最终结果。
- Step：一次模型请求及其对应的工具处理阶段。

在此基础上增加运行时阶段：

```text
understand / plan
model_request
tool_execute
await_hitl
await_async
verify
finalize
```

这些阶段主要用于状态和事件表达，不为了标记阶段而强行增加模型请求。

每个 Step 增加：

- 触发原因。
- 当前阶段。
- Tool Batch ID。
- 模型请求尝试次数。
- 是否等待外部事件。
- 是否需要验证。
- 下一步决策。

新增权威事件建议包括：

```text
turn.verification.started
turn.verification.completed
turn.completed
```

其中 `turn.completed` 应携带：

```text
completion_status
verification_status
evidence_count
unresolved_count
```

### 阶段 4：提升 Skills 与长期记忆质量

#### Skills 标准化

Skill 文件增加统一结构：

- 适用场景和不适用场景。
- 前置条件。
- 输入和输出。
- 执行步骤。
- 验证方式。
- 常见失败和恢复方式。
- 安全边界。
- 示例。

增加 Skill lint，检查缺少完成标准、缺少失败处理、指令矛盾和无法执行的宽泛描述。

继续接受 Skills 清单或正文真实变化带来的缓存失效，不引入动态尾部或通用 dispatcher 来规避语义变化。

#### 结构化长期记忆

长期记忆后续可以增加：

```text
content
scope
source
confidence
created_at
updated_at
expires_at
```

原则是只保存长期稳定事实，不保存临时任务状态；冲突记忆保留来源并交由 HITL 或后续流程处理。待核心工具质量稳定后，再从“整体注入”演进到按任务相关性检索。

### 阶段 5：模型策略和可选质量审查

最后再评估：

- 普通、平衡、深度推理模式。
- 按任务风险进行模型路由。
- 高风险任务的额外审查。
- 可选 critic / quality judge。

不默认给每个 Turn 增加审查模型调用。该策略会增加成本、延迟和缓存压力，只有当 A/B 评测证明它能显著降低高风险错误时才启用，并限制在特定任务或验证模式下。

## 5. 质量与成本指标

### 5.1 质量指标

- 端到端任务成功率。
- 指令遵循率。
- 工具选择和参数正确率。
- 工具失败恢复率。
- 结果验证覆盖率。
- 无依据成功声明率。
- 部分成功和未完成事项的表达准确率。
- 异步、HITL、取消和恢复正确率。

### 5.2 运行指标

- Turn / Step 数量。
- Tool Call 数量和并行度。
- 模型重试与工具重试次数。
- p50 / p95 延迟。
- 输入、输出 token 和成本。
- 上下文缓存命中率与失效原因。
- 工具结果溢出次数。

### 5.3 建议的硬性验收条件

- 严格验证场景中不允许出现无证据成功声明。
- 有资源冲突的工具调用不允许错误并行。
- 取消后不能产生新的工具执行。
- 异步任务必须以回调或最终状态作为完成依据。
- 空 stdout 必须能被模型正确识别为“命令成功但无输出”或其他真实状态。
- 关键失败必须在最终回答中明确体现。
- 前端状态必须由权威生命周期事件驱动。

成本指标用于观测和告警，不作为牺牲任务正确性的理由。真正发生语义变化的工具、Skills 清单和 Skills 正文导致的缓存失效按既定原则接受。

## 6. PR 拆分建议

建议按以下顺序实施：

1. Agent 质量评测框架和首批黄金场景。
2. 稳定 System Prompt 任务执行契约及提示词测试。
3. 工具 Schema、bash / linux_exec 结果契约统一。
4. 工具能力分类和安全并行调度。
5. 验证状态、完成判定和权威事件。
6. Skills 规范与 lint。
7. 结构化记忆和相关性检索。
8. 可选的深度推理和质量审查策略。

第一批开发应从第 1、2 项开始：先建立基线，再落地稳定的任务执行契约。这样后续每一个提示词、工具调度或验证逻辑的改动，都可以通过同一套场景判断是否真正提升了 Agent 质量。

## 7. 当前落地状态

### 阶段 0：已完成基础落地

- 新增 `node/internal/eval` 确定性评测包。
- 新增 12 个稳定 ID 的黄金场景。
- 新增 Trace、Scenario、Criterion、ScenarioResult 和 Scorecard 结构。
- 缺少 Trace 时显式失败，避免评测数据缺失造成假阳性。
- 已加入工具顺序、空输出、取消栅栏和完成验证等基础断言。

当前阶段 0 仍可继续增加真实模型 A/B 适配器，但不阻塞第一轮提示词和工具契约改进。

### 阶段 1：已完成第一轮落地

- 稳定 system prompt 增加任务执行契约，不包含动态计划、工具结果或实时状态。
- 子 Agent 移除默认过度确认行为，改为仅在关键信息、权限或安全边界不明确时询问。
- `bash_run` 和 `linux_exec` 增加 `status`、`target`、`exit_code`、stdout/stderr 字节数和截断标识。
- 交互终端读取结果增加 `output_bytes` 和 `output_empty`，明确区分空输出与未执行。
- 工具描述同步声明退出码、空输出和截断字段的语义。
- 已补充提示词和工具结果契约测试。

阶段 1 的后续工作是继续统一更多工具的副作用、重试和验证描述；工具能力分类、并行调度和后置验证属于阶段 2。
