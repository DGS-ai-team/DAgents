# 本机工作区写入方案（待实施）

## 目标与范围

Desktop 与 Node 固定运行在同一台机器。Desktop 直接读取工作区文件；本方案移除 Desktop 向 Node 发送工作区文件字节的路径，同时保留 Node 与 Agent 工具间已有的写入协调、文件版本冲突保护。它覆盖编辑保存、新建文件和导入本机文件，不改变模型工具自身的文件写入，也不涵盖模型供应商、Manage、历史媒体的数据传输。

当前 Node 的 `workspaceCoord` 在进程内协调路径及其祖先、后代范围的写入；工作区保存检查原文件 SHA-256，使用同目录临时文件发布。`write_file`、`search_replace` 和 `bash_run` 等使用同一协调器；参与情况应以具体工具实现为准。外部编辑器及没有参与该协议的进程不受该锁保护。

## 方案：Desktop 准备，Node 短事务提交

1. Desktop 原生层使用 Agent ID 向 Node 请求准备写入，声明工作区相对目标路径、操作类型（修改或新建）、预期版本（新建时要求不存在）以及文件大小。Node 验证 Agent、工作区和目标路径，签发一次性操作 ID，并在 Node 自有的受限暂存区域创建唯一文件。操作 ID 绑定 Agent、目标、操作类型和预期版本，设过期时间及大小上限；暂存文件路径只交给 Desktop 原生层，WebView 不得指定任意源或目标绝对路径。准备阶段不持有工作区协调锁。
2. Desktop 将编辑器文本写入暂存文件；导入文件时，通过用户选择器授权的源文件句柄向暂存文件流式复制。完成并关闭句柄后计算大小和 SHA-256，调用 Node 的提交接口，只发送操作 ID、大小和摘要等元数据，不上传文件内容。正文仍需从 WebView 进入 Desktop 原生层；该边界可先使用受限 IPC，避免宣称全链路零拷贝。
3. Node 再次验证操作 ID、Agent 状态、工作区归属、暂存文件身份及长度和摘要，拒绝链接、非普通文件、过期或已消费操作。用受限句柄读取暂存文件，避免检查后按路径重新打开而发生替换；若跨卷或文件系统不允许原子移动，将内容流式复制到目标目录的安全临时文件。临时文件准备期间不占用协调锁。
4. Node 取得目标路径的现有 `workspaceCoord` 租约，在锁内重新验证工作区和目标，重新读取目标当前内容并计算版本；修改必须匹配预期强版本，新建必须仍不存在。校验通过后，将同目录临时文件原子发布；在 Windows 和其他平台分别验证替换及创建语义。成功返回新版本、目标相对路径和大小，随后释放锁、清理暂存。
5. Desktop 仅在收到成功结果后更新基线和清除草稿。冲突、占用、权限不足、源文件删除、空间不足等均保留草稿并显示具体原因。用户可重新读取、比较、另存草稿或明确选择基于新版本再次保存；不能把“强制保存”设计成静默覆盖。

暂存目录由 Node 确定并限制容量、权限和生命周期，不放在 Agent 可浏览的工作区；启动时和定时清理过期操作。操作 ID 不是替代认证的安全边界：Node API、Desktop 命令窗口和文件句柄仍需各自校验。暂存文件和目标临时文件必须避免符号链接、Windows junction/重解析点和路径替换；私有 `.dagents` 目录保持不可从普通工作区操作访问。清理仅针对可证明属于当前产品的暂存文件。

## 并发、失败与语义边界

- **Agent 与 Desktop**：参与同一 Node 协调器的写入串行化；大型复制和用户选择文件不占锁，锁只覆盖最终校验和提交。等待锁时有超时、取消和明确的“工作区忙”反馈。
- **外部程序**：外部编辑器、终端脚本或不使用协调器的进程仍可能在最终校验后并发修改。原子替换能防止半文件，但普通文件系统通常不提供针对任意外部写者的原子内容 CAS，不能承诺完全消除竞态；应尽量缩短校验到发布的窗口，清楚说明这一限制。
- **重复请求**：一次性操作 ID 在进程存活期间记录提交结果，重复提交返回原结果，不重复写入。若提交后 Node 崩溃或响应丢失且重启后无法确认，应报告结果未知并重新读取实际文件、保留草稿；不能把相同内容的观察当成操作一定成功，也不能自动覆盖重试。
- **关闭或取消**：准备阶段关闭、复制中取消、Desktop 或 Node 崩溃不会发布目标；临时文件由过期清理回收。进入原子发布阶段后取消结果可能未知，应按结果未知处理。
- **源文件一致性**：导入期间若源文件变化，按源句柄和版本检查决定失败或明确要求重新选择，不能混合多个版本。新建及导入同名文件默认拒绝，不隐式覆盖。
- **容量与格式**：延续现有编码、换行、BOM、文件权限与冲突提示语义。文本保存上限、导入文件上限、暂存总量、单次超时和进度反馈在实施时明确配置与验收；大文件不可通过前端 Base64 拼接。

## 接口与数据流草案

```text
Desktop WebView → Desktop 原生：保存文本 / 用户选中文件
Desktop 原生 → Node：prepare(agent, relative_path, expected_revision, size)
Desktop 原生 → 暂存文件：本机写入或流式复制
Desktop 原生 → Node：commit(operation_id, size, sha256)
Node：验证暂存 → 准备同目录临时文件 → 获取 workspaceCoord
     → 校验当前版本 → 原子发布 → 返回新 revision
```

`prepare/commit/cancel` 均是产品内部控制接口，具体路由与返回字段以实现设计和测试为准；不要把暂存路径暴露给 WebView，也不开放通用任意本机路径写入命令。Node 依然持有提交权，因此这不是 Desktop 跨进程直接绕过协调器写工作区。

## 实施与验收

1. 先完成操作生命周期、受限暂存、大小限制和清理，并为正常、过期、重复、失败与崩溃结果添加测试。
2. 迁移文本编辑保存和新建，核对现有 SHA-256 版本、草稿、外部修改、编码和 BOM 行为；保留现有 Node 写路径作为迁移期间的回退，验证无调用后再删除。
3. 迁移原生选择器导入及剪贴板产生的文件，覆盖大文件、取消、重名、容量不足和跨卷。逐项移除 Desktop 写入二进制桥接、Node 旧上传及仅服务旧路径的代码和文档。
4. 在 Windows 原生程序做真实验收：Agent 与用户同时写入、共享工作区、长时间持有租约、外部编辑冲突、文件/目录删除、重解析点替换、进程中断、重复提交、目标存在及跨卷；检查日志不泄露文件内容或凭据。

此方案是下一阶段设计，不表示写入链路已经迁移。实施前应以产品实际并发规模和文件大小测量 IO 开销；若短文本的性能收益不足，不应为性能数字扩大协议复杂度。
