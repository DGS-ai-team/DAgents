本轮以隔离 Agent 和真实模型完成 CSV 核对、报告审批与交付。最大问题是长对话中的审批卡在视觉上消失；另有额度错误误分类、取消后的上下文延续、引用协议泄漏和窄资源区遮挡。

结论摘要

已完成的真实流程：DeepSeek 读取 CSV 并分析重复与异常金额；报告写入请求进入审批；通过本地 API 批准了确切的工作区写入；原生 Desktop 打开报告、引用 CSV 并修正措辞；Agent 随后更新并回读报告。

优先问题：长对话的审批卡在原生屏幕上仅剩一条分隔线，AX 仍读到完整审批内容；额度不足错误显示为配置错误；取消后相关后续请求仍会补做被取消任务的未完成部分。短对话中的批量审批卡可见，支持审批卡 flex 收缩假设，但未做 DOM 测量。

证据边界：原生审批按钮与多选交互未验收；两次原生 Stop 尝试时回合已自然完成，不能算停止通过。实际取消由 API 接受后取消，follow-up 也由 Luna 脚本通过 API 发送；后续长回复仅由 history/SSE 核对，没有 native 截图。

请求轮次：主 DeepSeek Agent 7 个人类请求轮次：前三轮分别有 3/2/4 个工具调用，两轮长文无工具，一轮 API 取消，一轮 API follow-up 后 completed。第二 Agent 2 轮：Qwen 额度失败，随后 DeepSeek 批量审批完成（1 项成功、1 项拒绝）。共 9 个人类请求轮次；这不是模型 API 调用总数，多步骤与恢复会产生多个模型步骤。

P0 · 审批阻断

长对话审批卡片不可见，用户无法在 Desktop 中决策

03 原生截图；AX可读；DOM根因未测

实测：DeepSeek 请求停在 pending_hitl。辅助功能树可见“需要确认”、中风险、purpose“生成 expense-review.md 复核报告”、拒绝和允许本次；原生屏幕仅在消息区末尾显示一条横线，卡片正文和按钮均不可见。连续两次 snapshot、向下滚动 560px、切换 Agent 再返回后仍一致。

对照：短会话中同批两个 write_file 审批清楚可见（12），因此问题与长消息流/布局空间相关的可能性高；当前没有 DOM 尺寸与 computed style 测量，不能宣称 flex 收缩已被证实。

高概率根因：.chat__stream 是纵向 flex 滚动容器；ApprovalBubble 直接作为 flex 子项，根节点设置 overflow:hidden 且未锁定 flex shrink。拥挤时可能被压至仅剩边框高度。工具组本身显式使用 flex:0 0 auto，审批卡没有。下一步应在原生 DOM 记录审批框 rect、高度、flex-shrink、overflow 和 stream 的 scrollHeight/clientHeight；临时禁用 shrink 验证。

建议：审批请求始终保持可见并可滚动到达，必要时为卡片保留内容高度或单独确保审批区域进入视口；不得以无障碍树可读替代视觉可操作。原生审批按钮/checkbox 本轮未点击，API 批准仅用于完成隔离工作流。

验收：长消息流和短对话中的待审批卡都完整显示标题、purpose、按钮；滚动、回到 Agent 和新事件更新不再将卡片压成细线；键盘与屏幕阅读器路径分别验证。

P1 · 错误恢复

额度耗尽被归类为模型配置错误，错误旁没有恢复入口

API 实测 + 04/11 原生截图 + 代码事实

实测：09:34:16，Qwen qwen3.7-plus 返回 HTTP 403，JSON error.type/code=insufficient_quota，原因为免费额度耗尽。Node 投影为 provider_configuration，Desktop 显示“模型请求或配置无效，请检查模型名称、接口地址和请求参数”。回合已失败终止，不是卡住。

恢复路径：错误文字旁没有设置/切换动作。失败后底栏 picker 可打开并选择 DeepSeek；列表显示 profile ID（如 deepseek-v4-flash），底栏显示模型名（如 qwen3.7-plus），两种标识没有说明，容易误读为不一致配置。

代码佐证与建议：Node provider error 按 HTTP 状态把 403 放入配置类、402 才归 quota；Desktop 虽已有 provider_quota 专用提示，但这次没有命中。让结构化错误优先识别额度信号，显示额度不足的准确原因，并就近给出切换模型/打开模型设置的明确路径；标签应区分“配置名称”和“实际模型名”。

验收：相同响应显示额度不足而非配置错误；用户可从错误位置切换模型或打开设置；picker 中 profile 与模型名称的关系清楚。回合终态解除发送锁。

P1 · 取消语义

取消回合后，相关后续请求仍可能完成被取消任务的剩余要求

API accepted/cancelled 事件 + API follow-up + history/SSE

实测：Luna backend API 返回 accepted 后约 1 秒取消，终态为 cancelled_by_user。相关 follow-up 也由 Luna 脚本通过 API 发送；Agent 补做了取消前任务中尚未完成的 50 节以及新消息末尾的要求。History 保留连续两个 user 条目；新消息没有被吞，也不是队列重放。约 7300 字符的后续回复仅由 history/SSE 核验，没有 native 截图。

影响与建议：保留用户输入作为历史，但将该任务明确标记为已取消。后续生成应优先响应最新意图；只有用户明确选择“继续该任务”时才恢复旧任务。界面简洁显示“已停止”；若本轮已有文件变更，说明已写入内容仍保留。无需删除历史或增加技术确认步骤。

验收：取消后发一条无关新请求，只回答新请求、不补做旧任务；明确选择“继续该任务”才续做；历史保留旧输入并标记已取消。Stop 按钮需在真实运行中单独验证。

P1 · 侧栏状态

当前 Agent 已完成，侧栏仍显示审批中的橙色提示

13–15 原生截图 + hydrate/API 字段 + 代码追踪

实测与字段：截图 13–15 中当前 Agent 仍有橙点；双方 hydrate 都是 completed、active=false、pending=null。GET /v1/agents 返回的 has_pending_hitl 在 false 时省略，而 has_unread=true。不能把省略的 false 解释为 Node 仍有待审批。

代码佐证与可能原因：Desktop 的橙点只读取 agent.has_pending_hitl（DesktopApp.vue:2042），不使用 unread；Node 的通知投影从 pending HITL 状态导出（notify.go:131–147）。更可能是 Desktop 未及时同步侧栏 Agent 列表，当前 Agent 的通知清除也没有被侧栏消费；根因尚未由事件追踪确认。

DesktopApp.vue:2042 · notify.go:131–147

建议：终态 hydrate/审批解决后及时刷新或更新对应侧栏 Agent 行；unread 提示与 pending approval 使用独立视觉语义。

验收：审批通过、拒绝或终态完成后橙点在一次状态更新内消失；切换 Agent 再返回仍与 pending_hitl 一致；仅 has_unread 时不显示审批橙点。

P2 · 信息层级

工具引用的内部版本协议泄漏到用户消息，并与附件卡重复呈现

08/10 原生截图

发送前，08 中的 CSV 引用 chip 清楚展示文件名。发送后，10 的用户消息正文又出现完整预览版本 hash 和“读取附近消息附带的工作区文件并结合位置查看内容”等内部协议文本，同时下方再次出现 CSV 附件卡。

建议：保留用户写的任务与一张清晰引用卡；把 revision、内部读取指令留在模型请求/可诊断细节，不拼回常规消息正文，也不要重复一个附件入口。

验收：普通消息只显示用户原话；引用卡显示文件名和必要定位；hash 与内部协议不出现在用户可见正文。

P3 · 结果摘要

混合审批结果折叠后只突出被拒绝项

14 原生截图

两项 write_file 经 API 分别批准和拒绝后，展开列表能清楚区分“已完成”和“已拒绝”。折叠父行只显示被拒绝项的 purpose，右侧显示“1项拒绝”，没有概括另一项已完成。

建议：折叠态用中性批次标题，状态简洁概括混合结果，例如“2 项工具操作”与“1 项完成 · 1 项未批准”；具体文件和结果仍在展开子行。

验收：一完成一拒绝时，折叠态能同时表达两种结果和数量；展开后每项仍显示准确状态，不能暗示被拒绝项已执行或自动重试。

P2 · 资源可读性

窄资源区压缩表格，展开 Dock 又遮住 CSV 末行

06/07/09 原生截图

应用导航和工作区文件树形成双侧栏，预览列只剩较窄空间，报告中的四列表格字段与内容多处折行。CSV 视图能读到 7 行、4 列，但金额值左对齐，CSV 第一行字段名看起来与普通数据行相同。09 展开 Dock 后，底部消息卡覆盖 CSV 预览最后一行。

建议：宽窗口维持分栏；窄窗口把文件树收为较窄抽屉或可收起栏。预览滚动区为底部 Dock/输入栏保留空间，用户可滚动看到末行；CSV 表头和数值列分别用表头样式、右对齐数值强化扫读。不要再叠加一排常驻面板。

验收：报告表格无需异常缩放即可阅读；Dock 展开时仍能滚到 CSV 最后一行；金额列右对齐且列名/首行语义清楚。

静态图不能证明多个工具状态切换时的连续动画、折叠父行高度是否全程稳定或子行展开状态是否保持；本轮不把这些说成已验收。批量结果截图显示仅批准的 review-checklist.md 被创建（421B），拒绝的 review-questions.md 不存在；模型未擅自重试，并在最终回复中明确说明未创建。

2 · 工具审批

原生审批控件未操作；决策经本地 API 完成

长对话里，审批请求“生成 expense-review.md 复核报告”进入 pending_hitl，但卡片视觉不可见（03）。短会话中的两个 write_file 批量请求正常显示风险、purpose、待确认状态、右侧 checkbox、拒绝本批和批准所选（12）。后续真实批次由本地 API 对 review-checklist.md 精确批准、对 review-questions.md 拒绝：前者创建 421B 文件，后者不存在；模型没有自行重试，最终答复明确报告未创建。13–15 记录结果、展开终态和参数详情。

原生审批卡实际批准/拒绝、多选 checkbox、展开参数均未在界面点击验收。API 决策验证了执行结果，不代表 UI 控件交互通过。

为避免通过自动化绕过安全决策，实际写入由本地 API 对确切的 workspace write 请求批准；不能把该工作流结果算作 UI 审批交互验收。
