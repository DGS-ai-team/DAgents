# Desktop 完整产品设计：缺口与补齐顺序

评估基线：2026-09-24 的 [当前界面图](visuals/current-desktop-mockup.png)、[交互原型](prototype/)、[技术方案](architecture/desktop-node-separation-plan.md) 与 [现有视觉系统](visual-system/)。这里评价的是**设计是否足以指导完整产品开发**，并不评价已有 Node 功能是否可用。

> 2026-10-20 更新：本文保留为历史设计审计。文中“保存远程 Node”等范围已取消；当前 Desktop 仅连接同机 Node。现行功能缺口和 Node 交互边界见 [Desktop 接入范围与 Node 交互收束](desktop-node-interaction-review-2026-10-20.md)。

## 已经具备

- **架构边界**：Desktop 默认连本机 Node，可保存远程 Node，但同一时间只激活一个；Agent/Session/Auto/Trigger 的权威数据仍在 Node。技术方案已经讨论原生 Shell、远程能力、浏览器侧会话、NodeFile / DesktopFile / Artifact、上传下载、截图、性能、安全和发布阶段。
- **核心工作区方向**：单行菜单、三类工作对象的侧栏、对话与资源页签、固定输入栏和收起消息时的紧凑活动摘要有图稿与可点击原型。
- **共享视觉资产**：有品牌 PNG、色彩 token 草案、功能图标 SVG 和 Node / Manage 视觉审计；原型完成了单一屏幕的视觉与交互验证。

这些材料回答了“系统大致如何组成、主界面长什么样”，还不能完整回答“用户在每种状态下如何完成任务”。

## P0：开发工作区前先冻结

| 缺口 | 当前问题 | 应交付的设计物及验收条件 |
| --- | --- | --- |
| **产品范围与版本边界** | 技术方案覆盖本机、远程、跨平台、浏览器、文件、Auto 等多阶段能力，原型没有明确首发范围。 | 一页产品定义：目标用户、首发任务、非目标、Windows 首发与 macOS/Linux 后续范围；列出 v1 必须完成的用户旅程与不做项。 |
| **信息架构与导航** | 三类侧栏对象和页签已有形态，但 Agent / 工作组 / Auto 的创建、编辑、归档、设置、跨 Node 切换和找回会话未贯通。 | 全局导航图、菜单命令表、侧栏条目动作表、页签生命周期表；从任意页面能找到节点管理、当前 Agent 设置和帮助，返回路径确定。 |
| **Node 连接体验** | 最新稿移除了顶栏快切，但仍需保存多个 Node、只激活一个；本地/远程识别、添加、认证、能力缺失和切换反馈没有界面。 | 本地初次启动、添加远程、连接失败、认证过期、版本不兼容、切换中、断线重连的逐屏流程；每屏明确当前 Node 与操作归属。 |
| **Manage 的产品边界** | 架构中 Manage 是可选控制面；Desktop 应内嵌哪些管理任务、哪些转至 Manage、没有 Manage 时如何降级，尚未定稿。 | 能力/权限矩阵和入口图；工作组、注册、反馈、管理员操作在 Desktop 与 Manage 之间有唯一且可发现的去向。 |
| **资源页签与对话并存规则** | 原型只模拟了终端/浏览器/文件打开与关闭。资源由 Agent 自动打开、用户固定页签、多个资源、切换智能体/Node、恢复窗口、未读与焦点抢占尚无统一规则。 | 页签状态机与状态图；明确哪些页签可关闭/恢复、何时自动切换、资源关闭是否停止 Node 进程、跨 Agent/Node 隔离及输入栏行为。 |
| **紧凑活动区与审批** | 消息区隐藏时，简化消息/工具/审批可能丢失上下文；审批详情、超时、重复请求、拒绝后的反馈尚无完整设计。 | 展开/收起、多个待审批、风险说明、允许一次/拒绝、过期/已由别处处理、键盘操作的状态稿；任何待审批都可回到完整上下文，审批对象和 Node 清楚。 |
| **关键用户旅程** | 当前仅有单屏演示，没有端到端可走通的产品流程。 | 至少打通 5 条：首次连接本机 Node→创建 Agent→首次聊天；远程 Linux Node→打开终端/文件；Agent 打开浏览器→用户接管/归还；收到工具审批→查看影响→处理；Auto 工作状态→进入其聊天/设置。每条覆盖成功、取消和失败出口。 |
| **设计与技术方案同步** | 技术方案第 3.5–3.7 节及后文的性能/验收条目仍写常驻三栏、Auto 总览、顶栏 Node 快切，和当前图稿冲突。 | 经确认的布局 ADR；改写方案中冲突的图、菜单分工、性能测量方式和验收条目，确保开发只读到一套规则。 |

## P1：完整产品设计所需

| 缺口 | 应补设计 | 完成标志 |
| --- | --- | --- |
| **页面与状态全集** | 欢迎/引导、节点管理、智能体/工作组/Auto 列表与设置、聊天、终端、浏览器、文件预览、设置、更新、诊断；各自的空白、加载、错误、离线、权限不足、只读状态。 | 页面清单与状态矩阵，关键状态有可点原型或高保真图；文案、按钮启用条件和恢复动作一致。 |
| **Desktop 专属设计系统** | 在共享品牌基础上冻结 Desktop 的浅/深色主题、文字层级、间距、密度、边框、阴影、图标尺寸、状态色、菜单/弹层/页签/卡片/输入/审批组件。 | 设计 token 与组件规格可直接映射到代码；和 Node/Manage 的共有项与差异项写清；正常/悬停/选中/禁用/焦点都有样例。 |
| **窗口与平台适配** | 自定义单行菜单与拖拽区、窗口控制、最小宽高、缩放、窄窗口资源显示；Windows/macOS/Linux 系统菜单、快捷键和托盘差异。 | 800/1024/1280/1440/1920 宽及高 DPI 截图；键盘焦点、窗口按钮和系统菜单在目标平台的行为表。 |
| **资源细节** | 终端多 session 与进程状态；浏览器页面/Node 归属、观看与接管、弹窗、下载；文件列表、预览类型、上传下载、打开本机文件与打开 Node 路径。 | 每类资源有任务流、失败态、权限提示与归属标签，明确“关闭 UI”与“停止远端任务”的区别。 |
| **Auto 与工作组体验** | Auto 状态、唤醒、待办、Dreaming、暂停/恢复、与普通聊天共用会话；工作组成员/任务/审批在 Desktop 中的入口。 | 普通 Agent、Auto、工作组在列表、会话、设置和活动提示上的差异完整且不混淆。 |
| **内容与可访问性** | 中文与英文文案、术语表、错误与确认语气、快捷键、屏幕阅读器名称、焦点顺序、对比度、减弱动画。 | 状态不用颜色单独表达；正文/大字与焦点满足既定对比度目标；纯键盘可完成关键旅程。 |
| **隐私、安全与信任提示** | 远程 Node 的凭据位置、上传目标、截图归属、浏览器 profile/下载落点、审批风险、断线后的执行状态。 | 用户在高风险动作前能辨认执行机器、文件去向和影响范围；提示与 Node 真实权限一致。 |

## P2：验证和交付

- **真实用户验证**：用至少三类任务（本机日常聊天、远程开发/资源操作、Auto 长期任务）做可用性测试，记录误操作、找不到入口和不理解执行归属的点。当前原型的测试是实现/视觉验收，不是用户研究。
- **性能与质量基准**：按技术方案测冷启动、空闲资源、长消息、终端输出、浏览器帧、PDF/大文件、远程延迟与恢复；把实测预算写进发布门槛。
- **设计交付物**：版本化页面清单、流程图、组件与 token 规范、状态矩阵、文案表、交互说明、可访问性检查、平台差异表和设计验收用例。原型中的演示数据需与真实 Node 契约分离。

## 建议的工作顺序

1. 先冻结 **v1 范围、导航和 Node 连接流程**，解决“用户从哪里开始、现在操作的是哪台 Node”。
2. 随后定稿 **资源页签 + 紧凑活动区 + 审批状态机**，这是当前新布局区别于旧 Web UI 的核心。
3. 补全五条关键旅程和页面状态矩阵，再扩展视觉组件库；不要先把当前单屏原型直接当成生产规格。
4. 依据确认后的布局修订技术方案，最后做跨平台、无障碍、真实用户与性能验收。
