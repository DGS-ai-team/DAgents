# 用户身份、Desktop 与共享 Node 的职责调整

日期：2026-10-13。状态：设计建议，尚未实现。本文修正将用户称呼归入 Node 全局配置的旧判断。

> 2026-10-20 更新：本文是身份和多用户的历史设计建议，不是当前访问方案。Desktop 现在只连接同机 Node，不支持远程 Node 配对或设备授权；当前产品边界见 [Desktop 接入范围与 Node 交互收束](desktop-node-interaction-review-2026-10-20.md)。

## 当前实现与缺口

- `shared/config/config.go` 的 `UserConfig` 只有全局 `preferred_name`，没有人类用户编号。
- `node/internal/api/agents_api.go` 将此称呼写入 Agent 的 `TurnOptions`；`promptcontext/reader.go` 将其拼入稳定提示词。所有访问者实际上共享一个使用者身份。
- `api/server_lifecycle.go` 的 HTTP Handler 目前只有启动错误、首配门闩与访问日志，没有按用户认证的 Principal。Desktop 发送 Bearer header 不等于 Node 已经认证了用户。
- `api/triggers_api.go` 的 HTTP 管理操作使用固定 `admin/local` Principal。Agent 工具侧的 Trigger 所有者校验已存在，但不能替代用户权限校验。
- `api/server_messages.go` 以 Agent ID 入队，没有可信的人类发送者；请求中的 `user_message_name` 不能作为认证依据。
- `llm/runtime_settings.go` 的供应商扩展 `user_id` 当前填入 Agent ID，它不是应用用户身份，也不能直接承担授权职责。

现阶段是单个本机使用者的实现，不能将它描述为已支持多个独立用户安全共享 Node。

## 身份模型

| 对象 | 含义 | 职责 |
| --- | --- | --- |
| User | 人类使用者 | 稳定 user_id、显示名称、首选称呼；同一人可以绑定多个 Desktop。 |
| Desktop | 一个用户配置下的客户端实例 | 随机 desktop_id、客户端偏好、独立可撤销的设备凭证；同一物理机器不等于同一用户。 |
| Node | 执行与持久化服务 | node_id、运行环境、模型配置、工具能力、Manage 连接与运行数据。 |
| Membership | 用户与 Node 的关系 | 当前 Node 内的用户编号、角色、启用状态及可选称呼覆盖；由 Node 确认。 |
| Connection | 某次访问 | 已认证 user_id、desktop_id、connection_id；断线重连不会产生新用户。 |

不要求此阶段建立全局账号服务。可以先使用 Node 本地用户记录与设备配对：同一人新增 Desktop 时绑定已有用户，而不是每台 Desktop 自动新增一个人。未来统一身份可以增加 issuer/subject 映射，避免现在将硬件编号永久当用户编号。

称呼不唯一、可修改；user_id 不随称呼变化。Desktop ID 使用随机标识，不以 MAC/IP/硬件摘要认证用户。同机判定和用户身份分别处理。

## 配置与数据归属

| 数据 | 保存位置与范围 |
| --- | --- |
| 外观、窗口尺寸、资源布局、连接列表、通知偏好 | Desktop 当前用户配置；布局按 node_id 分开。 |
| 用户首选称呼、显示名称 | 用户资料；Node 保存其认可的用户记录，不能由任意请求声明。Desktop 可缓存自己的资料。 |
| 当前 Node 内的角色、设备授权、可选称呼覆盖 | Node 的用户/成员记录。 |
| Node 名称、模型凭据、工具、Manage 配置 | Node；全局修改需要管理员权限。 |
| Agent 所有者和共享权限 | Node；默认个人 Agent，显式共享后允许授权成员访问。 |
| 对话作者、审批处理人、操作审计 | Node 持久化可信 user_id/desktop_id；作者名称可保留发送时快照。 |
| 已读位置 | 按 user_id + agent_id 保存；同一人的多个 Desktop 可以同步。 |
| 当前焦点、草稿和打开的资源页 | Desktop/连接范围；不修改其他使用者的 UI 状态。 |

第一阶段可沿用 Node 现有 SQLite 基础，增加少量身份、成员和设备绑定表，不引入独立账号服务器。设备秘密应保存于系统凭据存储，不放入普通 Desktop settings.json。

## 认证与权限

Node 验证设备凭证后建立请求 Principal，不能信任请求体自行填写的 user_id 或名称。设备绑定到用户，每个 Desktop 的凭证可以单独撤销。

首次本机初始化由受控的 Node 本地初始化流程建立管理员并配对 Desktop；已有 Node 由管理员授权新设备或成员。禁止“第一个连接者自动成为管理员”。远程访问沿用认证，SSH 隧道、loopback 来源和同机证明均不能替代用户身份。

第一阶段建议管理员/成员两种角色，资源授权同时检查 Agent 所有者或显式共享关系：

- 管理员负责 Node 初始化、成员/设备授权、全局配置与维护。
- 成员操作自己的 Agent 及获授权的共享 Agent；全局模型列表是否可见、可使用由 Node 决定，凭据不可导出。
- 审批还需要对应 Agent 的审批权限；共享聊天权限不自动包含审批、终端、文件、浏览器或屏幕权限。
- HTTP、SSE、PTY/WebSocket、附件下载、文件与浏览器帧都执行同一授权；不能只过滤侧栏列表。
- 本地 Node 监护仍核验 Desktop 启动进程的归属。Node 管理员角色不会自动赋予停止其他 Desktop/外部进程的能力。

初期产品范围建议为受信任成员共享执行节点。应用 ACL 不等于操作系统隔离；若允许不受信任用户在同一 Node 执行任意 Shell，需要另外设计进程、文件系统和凭据隔离。

## 对话与 Auto 的身份传递

共享 Agent 仍保留同一会话，消息记录标识不同发送者。Node 在鉴权后、入队前冻结请求者身份；排队期间切换 Desktop 或修改资料不会将回合作者改成其他人。

移除稳定 system prompt 中“唯一使用者称呼”的假设。Agent 的职责、手册、经验继续稳定注入；当前回合另提供 Node 确认的发送者信息。历史消息保留作者，不通过修改共享 Runtime 的全局 PreferredName 来切换用户，避免并发串用。昵称只是展示资料，不能成为模型指令或工具授权依据。

Auto 有人类所有者，可以显式共享给协作者。定时激活的执行主体是 Agent/服务，而不是最近一个发消息的用户；工具、Trigger 和审批仍受 Agent 权限与 Node 策略约束。系统激活只记录关联所有者，不冒充管理员。Dreaming、待办、经验与手册按 Agent 归属；个人用户资料和个人记忆必须有独立范围。

共享 Agent 中管理员/协作者能否改职责、待办、手册，需在资源权限中明确，不因为所有人可聊天就默认全部可编辑。

## 首配与界面

Desktop 默认连接本地 Node，外观不再作为 Node 首配步骤。进入流程时依次判断连接、认证、当前用户授权以及 Node 初始化状态。

- 新本地 Node：创建本机使用者资料并完成受控配对，管理员配置 Node 名称和模型；不同归属分区保存，失败可以分别重试。
- 已配置 Node + 新 Desktop：管理员批准设备配对，确认绑定哪个用户；不重复 Node 初始化，不重写已有模型。
- 未初始化 Node + 普通成员：显示等待管理员配置，允许修正 Desktop 连接或退出，不让成员填写全局配置。
- 同一人的另一台 Desktop：沿用已有 user_id 和角色，只建立新的 desktop_id 与设备凭证。

“用户资料完成”“Node 已初始化”“模型可用”分别表达。称呼是用户资料，不再是 Node 初始化门闩的必填项。Node 基本信息可完成而模型尚未就绪，UI 明确显示后者状态，不用单一 completed 标志代表一切。

用户资料入口放顶部 DAgents 菜单，Node 管理设置与 Desktop 偏好分开；共享 Agent 消息显示发送者以便辨认，个人单用户消息继续保持现有简洁样式。设置页面按权限呈现，但后端授权始终独立执行。

## 上下文、Runtime 与记忆的隔离粒度

目前 session.Manager 按会话维护 runtime；消息 API 以 Agent ID 定位会话，runtime 持有独立队列、消息、工具执行、压缩协调器和待审批状态。建议保持 Agent 实例这一执行边界，先不增加每个用户访问同一 Agent 都复制 runtime 的结构。

| 场景 | 执行与上下文 |
| --- | --- |
| 同一用户从多个 Desktop 访问自己的 Agent | 同一 runtime 与历史，设备只是不同访问入口。 |
| 两位用户使用各自的私人 Agent | 不同 Agent 实例和 runtime，历史、待办、经验、手册及 Agent 记忆分别授权。 |
| 多位授权用户协作一个共享 Agent/Auto | 一份明确共享的任务上下文和 runtime；消息保留作者，审批只允许授权用户处理且一次生效。 |
| 同一个 Agent 模板给不同用户个人使用 | 复用定义或模板，创建不同个人实例；不要把共享模板理解为共享历史。 |

共享 Agent 的参加者应理解这是一份共享任务记录。私人资料不注入共享上下文；仅隐藏 UI 消息不能阻止模型从已加载历史中读取信息。人员称呼在消息入队时以可信身份快照附带，不能修改共享 runtime 的唯一用户字段。

每个工具调用的有效权限受 Agent 配置、当前回合执行主体和 Node 策略共同约束。人类回合在排队时确定执行主体；Auto 定时回合由服务身份执行，不能继承最近一个操作者的身份。权限撤销后需要在新的敏感操作执行前重新授权，不能依靠启动时永久缓存的角色。

当前记忆只有 agent/global 两种范围。多用户方案需加入用户范围，并约束 Node 全局记忆为明确共享的知识：个人资料、偏好和私人 Agent 提取出的信息不能自动汇入全局库。共享 Agent 的经验与 Dreaming 仍归 Agent；个人记忆只在符合资源共享关系的上下文使用。

应用访问隔离不能改变 Node Shell 的操作系统权限。共享工作目录中的文件仍是共同资源；若目标是互不信任使用者的强隔离，还需独立工作区、凭据和进程沙箱，不能仅以 user_id 或 runtime 分开宣称实现。

## Desktop 登录与本地身份的建议

选择本地优先模式，不强制首次启动创建云账号或每次打开应用输入密码。

1. Desktop 首次运行可创建本地用户档案（profile_id、显示名称、偏好），并生成当前客户端实例 desktop_id。这个档案是客户端资料，不是 Node 授权凭证。
2. 第一次访问某个 Node 时完成受控配对。Node 建立或选择已有用户记录，返回绑定 user_id 与 desktop_id 的设备凭证，并确认角色。每个 Node 都保存自己的认可结果。
3. 日后启动使用系统凭据存储中的设备凭证自动认证。Node 离线时可以打开 Desktop 本地设置，不能假定已获权或绕过 Node 验证访问数据。
4. 第二台 Desktop 访问相同 Node 时，通过授权流程绑定原来的 Node 用户；新建本地档案不会自动证明它与另一台 Desktop 是同一个人。凭证单独签发，不直接复制管理员秘密。
5. 共用 Desktop 可切换独立用户档案；账号切换要关闭旧事件流、清理旧资源和缓存、重新认证。初期可以先支持每个操作系统用户一个 Desktop 档案，避免未经实现就承诺安全共用同一 OS 登录会话。

没有统一身份服务时，Node 认可的 user_id 以该 Node 为命名空间；跨 Node 应使用 node_id + user_id 区分。Desktop 本地档案可以保存每个 Node 的用户绑定，但同名或相同 profile_id 不会自动授予跨 Node 权限。未来接入统一身份时增加 issuer/subject 映射即可。

远程 Node 首次连接必须认证并完成管理员允许的配对，不能仅提交自建 UUID 和昵称。节点管理员的授权、凭证签发、撤销与有效期独立于应用 UI 的“登录”外观；完整认证协议应使用成熟实现并在设计阶段专项审查，不自制密码或令牌算法。

## 建议开发顺序

1. 固定 User/Desktop/Node/成员关系及鉴权 Principal；配对、撤销与管理员本地初始化先闭环。
2. 接入 Agent 所有者和共享授权，覆盖所有传输与资源；替换 HTTP Trigger 的固定 admin/local。
3. 将可信作者身份传入消息队列、历史、审批与审计；调整提示词与 Auto 服务身份。
4. 拆分称呼、Node 初始化和 Desktop 偏好，再改首配页与资料/权限 UI。
5. 用两位用户、三台 Desktop、同一 Node 验收：同用户多设备绑定，改称呼不影响另一人，未授权资源不可访问，两个设备审批冲突只接受一次，撤销即时生效，Auto 在用户离线后继续工作。

这里只确定方向，没有修改当前 API、数据库或首配页面。完整多用户认证与授权上线前，现有本机模式的能力范围应继续明确。
