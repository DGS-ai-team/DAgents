# Auto 数字员工暂停交接（2026-09-09）

用户要求：收尾当前修改后暂停开发。本文是暂停时的状态快照；早期实施台账按时间保留的“尚未接入”等描述，应结合较新的维护实施记录阅读。全计划未完成，不以单元测试代替真实模型及产品验收。

## 产品和运行逻辑

- 普通 Agent 面向交互任务；Auto Agent 保留闲时聊天能力，增加长期岗位、业务周期、收尾决策和唤醒安排。岗位跨周期存在，不能靠新建周期重置累计预算。
- 触发器和事件源绑定 Agent 身份；模型操作自己的安排。每轮结束通过结构化决策明确继续、等待或结束，再投影为下一次唤醒。
- 同一 Agent 共用执行槽，聊天及业务优先于日常维护；取消维护后等待实际退出再释放，避免并行修改。
- 每日维护分事实记忆与手册两个阶段。事实记忆仍使用独立 SQLite 事务；手册内容、层级、索引和修改历史均在指定文件目录中，模型通过受限文件工具自主维护。
- 手册执行在调用模型前绑定真实 session、turn 和当时的根目录。恢复核对实际轮次日志、用量、文件来源历史与记忆操作，再原子结算；核对结算与恢复整个批次是独立动作。
- UI 已有类型区分、智能体/工作组/自主智能体分组、Auto 总览和设置入口。同目录仅用于组织展示，不合并身份和权限。Manage 汇总不替代 Node 的执行权威状态。

## 已有实施成果

触发归属、员工与周期、定时收尾、事件源与探针、共享执行槽、累计预算、受限临时授权、维护 controller、文件手册与恢复接口均已有实现和定向回归证据。设置页已接入逐项“核对并结算”，保留未保存草稿，避免把待恢复误显示为完成。

当前最后收尾项是手册无实际修改的写调用：由工具记录实际文件摘要，运行时持久化绑定 receipt/session/turn/tool call 的 `handbook.noop` 事实；来源历史为空时，API 要求每个写调用有唯一匹配事实，不能依据模型说“完成”放行。该项验证结果见维护实施文档的最新记录。

## 尚未闭环的缺口

1. **未知费用归属。** 旧维护状态只有全局 unknown 标记，缺少逐来源贡献记录。目前拒绝结算 unknown child，不能安全地通过某个子执行清除全局未知。需来源账本及历史未知状态处置方案。
2. **历史证据兼容。** 旧执行缺少绑定目录、真实 turn 或 no-op 事实时不能推测补齐，仍需保留待处理状态。
3. **最新版本真实模型验收。** 之前两次定时唤醒真实调用只证明此前的定时链路；新版每日维护、恢复、事件探针、对话修改岗位后读回、至少两个完整岗位周期仍需真实配置 LLM 验收。
4. **Node/Manage 联调与视觉。** 浏览器连接的旧 Node 尚未完整更新；前端构建和组件测试不等于新版所有页面、窄屏及 Manage 实际上报验收。既有组合重启操作被自动审批审查拒绝，未将其记录为成功。
5. **审批策略。** 已有范围受限的临时授权；LLM 风险判断仍是影子观察，不是完整自动审批机制，不能宣称已实现只审批少量高风险操作。
6. **持续运行与故障恢复。** 已有针对性事务、取消、幂等及重启测试；全链路长时间运行、跨周期故障注入和最终权限审计仍未完成。

暂停后不继续扩展功能，也不推送或部署。恢复开发时先核对工作区与运行版本，再优先处理费用归属和最新版本端到端验收。
