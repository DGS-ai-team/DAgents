# 普通 Agent 与 Auto Agent 产品方向评估

评估日期：2026-09-08。依据当前工作区实现、真实模型验收、Node/Manage 视觉验收及本轮提交审查。本文中的“建议”是后续产品方案，不表示功能已经实现。

## 结论

DAgents 应坚持“组织自有机器上的可管理 Agent”定位。普通 Agent 负责当下的人机协作，Auto Agent 负责用户委托后跨时间推进的工作。两者应是可辨识的 Agent 类型，使用同一套身份、记忆、模型、工具与执行机制，各实例的权限和记忆启用状态仍由配置决定；Auto 的差异来自持续任务责任、受控唤醒和结果回报，而不是默认拥有更高权限或更强模型。

普通 Agent 是低门槛主入口，Auto 是值得继续投入的差异化方向。当前已具备单 Node 受控执行 MVP，但距离可长期复用的产品仍有关键缺口：任务周期、持续观察语义、结果汇总与待处理入口。下一阶段应优先补齐这些，随后扩大跨机治理，不先堆更多触发器或工作流画布。

## 两类 Agent 的定位与形态

| 维度 | 普通 Agent | Auto Agent |
| --- | --- | --- |
| 用户委托 | “现在和我一起完成这件事” | “在约定范围内持续推进，重要时再找我” |
| 产品角色 | 交互式工作助手 | 持续负责某类工作的助手 |
| 时间边界 | 当前请求或有限任务回合 | 跨多次唤醒、等待与运行，直至完成、暂停或终止 |
| 默认入口 | 聊天工作台 | 仍可聊天，但清楚展示当前任务、下一次唤醒和待处理项 |
| 输出重点 | 当前回答、修改、文件、工具结果 | 相对上次的变化、累计进展、完成证据、需要人决定的问题 |
| 主要控制 | 发送、停止当前执行、工具审批 | 启用、暂停后续运行、停止任务、预算、截止与恢复核对 |
| 适用场景 | 临时分析、文件处理、代码协作、诊断和交互式操作 | 分批处理积压、定期检查变化、等待条件满足后跟进 |
| 成功指标 | 任务正确性、响应时间、有效操作次数 | 达成率、单位结果成本、人工介入次数、无效唤醒比例 |

两种类型都可以执行复杂任务、使用工具和保留记忆。普通 Agent 并不等于只能问答，Auto 也不等于永不停机。选择类型时应描述“工作方式”，避免用高级/基础暗示能力等级。

普通定时任务仍可表达用户预设的固定动作，例如定时生成一份摘要。它与 Auto 的区别应落实为：Auto 有持续目标、检查点、累计资源约束与受控的后续安排。不能仅以“有没有定时器”划分，否则两类概念会重叠。

## 当前已实现与边界

- Agent 类型保存为普通或 auto；Auto 的任务设置位于智能体设置中，创建后需要配置并启用。
- Auto 复用所属 Agent 的模型、工具权限与工作目录，使用专用执行会话保存自动运行记录；主聊天空闲时仍可以正常对话。
- 主聊天可以通过 `autonomy_get` / `autonomy_update` 查看、修改本 Agent 已有目标、完成条件、后续时间或暂停，修改可从设置读回。当前工具不能创建或恢复任务，也不能提高限额或重置用量。
- 自动运行使用 checkpoint 汇报进展和证据，受运行次数、Token、截止时间及最小唤醒间隔约束；忙碌时延后，不依赖 Manage 才能运行。
- 任务已完成或停止后，目前不能在原 Agent 内开启新的任务周期。必须新建 Auto Agent 是当前 MVP 的产品限制，不应当作长期设计。
- 预算按已报告用量在请求边界检查，不能宣传精确费用封顶。未知执行需要人工核对，不自动重放。
- Manage 已具备注册、协作和反馈管理，不等于已经具备集中管理各 Node 自主任务的产品面板。

代码入口：`node/internal/api/autonomy_api.go`、`autonomy_tools.go`、`goals_api.go`，`node/internal/goals/`，`node/webui/frontend/src/components/AgentAutonomyPanel.vue`。真实执行与视觉覆盖见设计目录中的验收记录。

## 建议的交互结构

### Node：一个 Agent 工作台，两种信息重点

保留统一导航与聊天交互。列表中明确“普通 / Auto”类型；Auto 附带一个可读状态，例如“等待下次检查”“运行中”“待审批”“暂停”“已完成”。不要仅靠颜色传达状态，也不要把“空闲”当作“任务停止”。

普通 Agent 默认只突出对话和工作产物。Auto 聊天顶部应提供可折叠的任务摘要：目标、最近结果、下一次唤醒、剩余次数/用量以及暂停入口。详细设置仍放在智能体设置，满足用户的一项一行布局偏好。这样既能随时聊天，也不必进入设置才能知道它在做什么。

运行记录应围绕任务周期组织：概览、进展、产物、运行历史、待处理。原始工具日志放在展开层。主聊天只接收关键结果摘要与链接，避免每次定时检查都灌入一段长消息。

通过对话调整任务后，应出现结构化回执：改了什么、何时生效、保存是否成功。模型自然语言回复不是修改成功的证据。运行中收到修改请求时，明确显示待本轮结束；用户需要立即介入时提供暂停或停止。当前还没有完整的调整草案/延后应用队列，应标为后续功能。

### Manage：面向管理员的监督视图

建议后续增加跨 Node 的 Auto 总览，按“需要处理”优先排序，显示所属 Node、责任人、目标、最近有效进展、下次运行及用量。管理员主要执行查看、暂停、收紧限额、处理授权与追溯，不重复 Node 的完整聊天界面。

Node 是执行与本地权限的最终边界。Manage 下发操作应通过已认证链路到 Node 并回传实际结果，不能把管理端按钮点击当作已停机。Node 离线时显示状态更新时间与待下发操作，不能显示虚假的实时成功。

管理员的跨 Node 操作需要独立设计角色权限与审计，目前不能把已有单管理员鉴权描述成细粒度 RBAC。

## 能力与管理边界

| 能力 | 共用基础 | Auto 需要增加的约束或呈现 |
| --- | --- | --- |
| 模型 | 同一配置体系，按任务质量选型 | 可先共用模型；后续再按观察/执行阶段优化，避免过早增加配置维度 |
| 工具 / Skills | 一致的能力目录和本地 policy | 后台执行应采用可独立收紧的权限集合；该独立集合尚属建议 |
| 记忆 | Agent 身份与记忆连续 | 任务检查点、业务产物与长期记忆分开，避免将临时状态写成长期事实 |
| 调度 | 复用 Node scheduler | 目标状态决定是否续跑，避免任务完成后定时器仍有独立生命 |
| 副作用 | 使用已有审批与取消 | 未知结果核对、重试去重；后续按工具补偿能力分类 |
| 通知 | 状态与消息入口 | 仅在结果变化、完成、待审批和异常时提醒；普通无变化检查静默 |
| 资源 | 同一机器上的执行资源 | 自动任务让位于交互；后续加入资源锁、并发额度与运行窗口 |

Auto 的累计任务预算与日常聊天消耗应分别显示：前者控制授权的后台任务，后者属于用户主动交互；不能把任务预算冒充整个 Agent 的费用上限。后续可补 Agent/Node 总配额，但不能让模型通过切换通道规避后台限额。

## 首先解决的产品缺口

1. **任务周期复用。** Agent 身份长期存在，Goal 是一次委托，Run 是一次执行。用户显式“开始新任务”创建新周期；旧周期终态和费用保留，不复活旧 Goal。初期仍限制一个 Auto Agent 同时一个活动周期。
2. **区分完成型任务与持续观察。** 分批处理完成后结束；观察任务在没有变化时仍属有效检查，不能简单累积为“无进展失败”。需要明确 `无变化 / 有进展 / 阻塞 / 已完成` 的结果语义、观察期限和检查预算。当前不能承诺无限期监控。
3. **结果与待处理入口。** 从“运行了几次”升级到“产生了什么、有何变化、现在需要我做什么”。先做本 Node 汇总，再扩到 Manage。
4. **对话调整回执。** 先保证保存、读回、生效时机和历史可追溯，再扩大自然语言控制范围。提高预算、扩大权限、新周期启动仍由用户明确授权。
5. **长时可靠性验证。** 进行持续运行、断网、进程重启、审批等待、工具超时和未知副作用演练，记录每种情况下的恢复依据。

这些属于下阶段建议。本次代码提交的验收目标是当前受控 MVP 的一致性，不将新周期、集中治理和长期稳定性试验伪装为已交付。

## 推荐的首批场景与验收指标

| 场景 | 交付边界 | 必须验收的结果 |
| --- | --- | --- |
| 分批处理文件积压 | 限定目录、数量与产物格式 | 可恢复进度、无重复处理、完成清单与失败原因 |
| 资料/报告变化观察 | 明确数据源、检查间隔和期限 | 无变化不打扰，有变化有对比证据，过期停止 |
| 条件满足后生成草稿 | 条件可检查，动作先限为生成产物 | 未满足不执行，满足后不重复产出，结果可追溯 |

优先使用只读检查和生成可审阅产物的场景，待副作用恢复机制完成后再扩大无人值守外部操作。对简单固定脚本，不应强行每次调用 LLM；对依赖连续人工判断的任务，普通 Agent 更合适。

建议试点指标包括任务达成率、每次有效产出的 Token、人工介入次数、误报率、无变化检查比例及恢复成功率。先采集基线再确定阈值；当前少量合成文件验收不足以给出商业 SLA 或收益承诺。

## 外部参考与取舍

OpenClaw 将定时执行、Heartbeat、后台任务和生命周期事件区分为不同机制。这支持 DAgents 保持统一调度基础、按用户目的组织 UI，而不是把每个机制都作为顶层功能。此处是产品推论，并非直接复制上游结构。[OpenClaw Automation](https://docs.openclaw.ai/automation)

Letta 的后台 dreaming 用于整理会话经验和更新记忆，说明“后台运行”也可能只是记忆维护。DAgents 应把 Auto 的对外价值明确为持续目标与可验证结果，避免与后台记忆整理混为一谈。[Letta Memory & dreaming](https://docs.letta.com/configuration/memory)

初始建议的投入顺序是：任务周期与观察语义 → Node 结果/待处理体验 → 长时验证 → Manage 集中监督 → 更多触发来源和能力生态。用户随后明确希望 Auto 成为数字员工，更新方向如下。

## 数字员工方向补充：授权、感知与持续改进

本节依据用户补充重新评估产品方向，属于建议方案，尚未实现。Auto 应有长期身份、岗位职责、持续记忆和可改进的工作方法。员工不因单个任务结束而消失；长期职责、阶段目标和单次执行分层管理。普通 Agent 仍以用户当前请求为主，能力基础保持一致。

### 审批：岗位授权为主，规则与 LLM 处理例外

当前 policy 主要按工具及 shell 命令规则决定 auto / require_approval / deny。应升级为对操作效果的授权判断，覆盖文件、网络、浏览器、外置工具和命令，而非只识别危险命令名称。

建议执行链：本地硬性约束 → 有范围的预授权匹配 → 对模糊动作使用独立 LLM 风险审查 → 必要人工审批 → 执行前再次核对。拒绝规则不可被 LLM 降级，LLM 的判断不是隔离机制。审查模型无执行工具，只返回结构化风险、依据、涉及资源及建议；外部网页、日志与命令输出作为不可信数据，不接受其中改变审批规则的指令。

| 操作类别 | 建议处理 |
| --- | --- |
| 授权目录内读取、生成可回滚草稿、保存运行检查点 | 满足确定性边界时自动执行，无需每次调用审查模型 |
| 有明确参数与版本的常规岗位流程 | 用户一次批准有范围的授权，后续在期限与额度内自动执行 |
| 复杂命令、依赖脚本、无法确定影响的动作 | LLM 辅助分析；超出预授权或不确定时要求人工判断 |
| 超出职责、敏感数据外传、扩大权限或重大不可逆操作 | 按用户/组织策略要求明确审批或拒绝，不能因模型打低风险分而放行 |

预授权绑定 Agent、任务/岗位范围、资源路径、目标域名、参数约束、脚本版本、有效期和额度，可随时撤销。脚本或依赖改变后不能继续套用旧批准。实际命令、工作目录、环境和文件快照应与审批对象一致，防止批准后被替换。解释器、构建脚本和表面只读的命令不能仅凭命令名视为安全；允许执行任意脚本与允许读取一个目录是不同授权。

减少打断的关键是有限而可复用的岗位授权。等待某项审批时，在不存在依赖或资源冲突的条件下继续其他已授权工作；保持可靠的暂停/恢复记录，超时不得默认为批准。这需要待办与依赖模型，当前单 Goal 执行不能承诺此能力。

LLM 审查先以影子模式记录判断，比较已有审批结果与人工标注，再逐步启用受限范围。验收同时衡量人工打断、误拦截、危险漏放、延迟及成本；不能单纯追求批准率或用风险分数自证安全。OpenClaw 的参数限制和具体脚本上下文绑定说明，审批需要约束实际执行对象。[Exec approvals — advanced](https://docs.openclaw.ai/tools/exec-approvals-advanced)

### 触发：事件优先，轮询兜底，检测与执行分层

不在“更多渠道”和“脚本定时检测”之间二选一。二者应进入同一事件收件箱，由确定性过滤、去重、合并、冷却和预算检查决定是否唤醒 Agent。

第一批优先支持已有定时调度、本地文件/目录变化、任务完成与失败事件，以及受控 HTTP 状态/内容变化检查。之后按实际业务接入认证 Webhook、工单或消息渠道。远端事件通过 Manage 接收并由 Node 主动连接获取，保持现有出站通信形态；无需要求每个 Node 开放公网端口。

检测器可以是不调用 LLM 的脚本或结构化探针，返回 changed / unchanged / error、事件 ID、摘要与证据引用。无变化只更新检查时间；检测失败与无变化分开记录。需要语义解释时才调用轻量分类，真正需要规划和行动时才启动完整 Agent。

不能恢复已移除的任意 `condition.cmd` 宿主执行路径。自定义检测脚本需经注册与授权，限制解释器、版本、输入、权限、环境、网络、时长和输出大小。自称只读不是只读隔离；需要 OS/容器等实际限制才能作相应承诺。

事件携带来源、租户/Node/Agent 范围、发生时间和去重身份；不把事件正文直接升级成任务指令。处理重复与乱序、断线补取、退避重试、积压上限和漏事件轮询对账。调度必须明确时区、工作窗口、休眠恢复和错过的日程如何合并。

### 持续改进：让方法演进，让职责与授权保持可控

数字员工建议维护五层信息：

| 信息层 | 谁可以修改 |
| --- | --- |
| 岗位职责、组织规则、权限和资源上限 | 用户/管理员；Agent 只能建议变更 |
| 阶段目标与优先级 | 用户设定边界，Agent 在授权内拆解与重排；扩大职责需要确认 |
| 工作手册、任务提示模板、常见问题处理方法 | Agent 可提出版本化修改，低风险改进经验证后自动生效 |
| 事实、偏好与经验记忆 | 按来源、时间、范围与有效期整理；冲突和不确定性需保留 |
| 执行日志与证据 | 保留事实记录，不由复盘改写历史以证明成功 |

每日在配置时间运行维护任务：读取新增记录 → 提取有证据的经验 → 去重、识别冲突与过期内容 → 生成记忆/手册变更 → 用固定案例回放验证 → 应用通过的版本 → 保留回滚点与简短报告。没有新增材料时跳过模型整理；维护本身有独立额度，也计入 Agent 总资源消耗。

可自动改进的例子是“某种错误先检查指定配置”“报告按用户已确认的格式生成”。不可自动改写的例子是扩大业务目标、删除验收条件、关闭审批、修改核心安全指令或提高预算。任务提示模板与用户/系统约束分层加载，Agent 可写的手册不得覆盖更高优先级规则。

这能产生可观察的学习效果，但不会自动训练模型权重，也不能保证每天单调变强。只有固定验证集、真实结果和后续退化检查支持的版本才能认定为改进；避免同一模型既修改规则又独自宣布变好。Letta 的 dreaming 也将后台复盘落实为经验整理与记忆更新。[Memory & dreaming](https://docs.letta.com/configuration/memory)

### UI 与管理呈现

Auto 工作台增加岗位摘要、今日工作、待审批、最近成果、下次检查和最近复盘。设置中按一项一行组织“职责与目标、工作时间、触发来源、授权范围、记忆与改进”；高级参数折叠。用户通过对话调整工作安排后，展示实际配置差异与生效时间。

改进记录展示“为什么改、改了什么、验证结果、当前版本、回滚”，不以虚构的成长分或人格等级代替证据。审批卡片突出真实影响和授权范围，可批准单次或明确受限的一类操作；不能把“以后不再问”解释为无限权限。

Manage 后续承担员工目录、职责模板、组织权限上限、待处理队列和审计。批准岗位授权与查看日常成果是管理的主要动作，本地 Node 继续执行最终权限检查。集中治理属于后续实现。

### 调整后的实施次序与验收

1. 员工身份与任务周期分离，定义职责/目标/手册/授权的所有权及运行状态。
2. 受限岗位预授权与确定性操作检查；LLM 审查先做影子评估，后做受限例外判定。
3. 统一事件收件箱与低成本探针，先覆盖本地变化和定时兜底。
4. 每日记忆整理与手册版本改进，加入验证、回滚和维护预算。
5. 结果/待办 UI、更多业务渠道和 Manage 集中监督，并进行连续运行故障演练。

首个试点可选“报告助理”：在限定目录检测新增数据，自动生成草稿，缺失数据形成待办，只有外发或超出授权才申请审批；每日总结格式偏好与处理失败经验。验收同时覆盖重复事件不重复执行、无变化不启动大模型、脚本变更导致授权失效、审批等待不丢进度、复盘错误可回滚及断网重启恢复。

## 触发器归属与 Auto 收尾决策评估（2026-09-08）

以下为后续设计建议，尚未实现。

### 当前实现与缺口

模型工具已按运行时 Agent ID 限制 trigger_list/get/update/delete，创建时也绑定当前 Agent；属于其他 Agent 的触发器不能通过这些工具读取或修改。ManagedGoalID 非空的触发器由目标运行时管理，模型不能直接修改或删除。因此不应把当前实现描述为“模型可以任意改别人的触发器”。

归属目前借用 TargetAgentID，没有独立 owner。工具先读取并检查归属，再调用存储修改；存储 UpdateTrigger 在锁内不检查调用者归属，而管理 API 可以修改 TargetAgentID，存在检查与写入之间目标变化的并发窗口。管理 API 的全局查看是管理员能力，不能直接等同于漏洞，但必须与 Agent 身份区分。拥有宿主机命令或本地网络能力的 Agent，也不能仅靠工具层过滤实现完整隔离。

goal_checkpoint 已有 next_wake_at，并检查最小间隔与截止时间；成功执行加 done 和非空证据会结束 Goal，未完成则进入等待。现有字段尚不足以明确表达“等待事件”“无变化”“岗位周期结束后继续履职”等不同状态。

### 所有权与控制权

采用独立且不可由模型修改的 owner_agent_id，TargetAgentID 仅表达执行目标。默认只允许面向自己的调度；跨 Agent 委派必须走显式授权流程，不能通过改目标获得控制权。创建者、控制器类型、目标周期 ID、版本号独立记录；旧数据按当前目标迁移归属，无法解析的记录禁用并交管理员处理。

Agent 只能查看自己的触发器及执行历史。普通触发器可在授权内增删改；目标续跑和每日维护等系统管理触发器可查看，但通过对应的任务/维护配置修改。管理员仍可全局查看、暂停和调整，明确记录操作者及原因。这里的“自己”指 Agent 身份；Node 用户和 Manage 管理员的组织权限是另一层，不能混为一谈。

在服务/存储边界统一执行身份、归属、控制器和版本校验，与修改在同一原子操作中完成。覆盖列表、详情、更新、删除、手动触发、恢复、历史和事件订阅；拒绝响应避免泄露他人资源是否存在。身份来自可信运行上下文或受限凭证，不接受请求体自报 Agent ID；Agent 不应持有管理员凭证。需要结合网络和进程权限约束，防止通过通用执行工具绕过 API 权限。

### Auto 的收尾协议

每轮结束前要求模型提交结构化决策：本轮结果、目标是否完成及证据、是否需要后续动作、下次时间或等待事件、理由和预期推进内容。由运行时验证并在本轮成功结束后提交调度意图；中途 checkpoint 仅作为候选。尽量纳入当前轮收尾，不额外固定调用一次模型。

| 收尾结果 | 后续行为 |
| --- | --- |
| 本轮完成，目标未完成 | 提议下次执行时间，运行时检查额度、期限、最小间隔和工作时间 |
| 等待外部变化 | 注册受限事件/探针条件，必要时设置低频兜底；无变化不启动模型 |
| 一次性目标完成 | 关闭该目标续跑，不要求模型强行找下一件事 |
| 常驻岗位本周期完成 | 保留已完成周期；依据已授权岗位安排下次检查或新周期 |
| 待审批、预算耗尽、未知执行结果或人工暂停 | 不允许通过创建触发器绕过阻塞或自行恢复 |
| 没有有效收尾决策 | 进入可见的待处理状态；仅对已配置的周期职责使用有限兜底，不无限盲目重试 |

“任务完成”和“员工停止履职”分开：员工可以持续存在，业务 Goal 可以完成。模型可在职责范围内调整计划，不能自行扩张职责、提高预算或把已完成 Goal 重新激活。正常对话修改计划也走相同的配置校验与版本控制，防止与正在收尾的旧运行相互覆盖。

目标续跑应更新同一受管理调度意图，而非每轮调用 trigger_create。使用 Agent、任务周期与用途作为幂等标识，结合版本和持久化提交/恢复机制，处理重试、重启和迟到回调。人工停止优先于旧运行的调度建议。每日复盘使用独立维护计划与额度；暂停单个业务目标不必停止岗位维护，但停用整个 Auto 应停止所有自主唤醒，并在 UI 中解释清楚。

### 优先级和验收

1. P0：补齐统一归属、可信身份及原子权限校验；验证跨 Agent 猜测 ID、历史读取、恢复、目标变更竞争和通用工具绕过边界。
2. P1：结构化收尾协议和幂等续跑，明确等待事件、无变化、完成、阻塞；验证重复回调不多建触发器、完成不复活、人工停止压过迟到结果。
3. P1 后续：员工身份与业务周期分离，支持同一 Auto 连续承接周期；再接入每日维护。验证正常聊天、计划更新和运行收尾并发时配置不被覆盖。

UI 在智能体设置内展示“触发与工作安排”，标注手动/周期任务/每日维护来源、下次唤醒时间和原因；系统管理项跳转到对应配置。管理员的全局触发器视图用于诊断，日常用户围绕员工与任务安排工作。
