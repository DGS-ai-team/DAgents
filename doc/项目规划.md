# DAgents 项目规划

## 仓库与子项目划分

| 子项目 | 目录 | 职责 |
|--------|------|------|
| **Register 中心** | `register_center/` | 策展型 Agent 目录：`agent_id` → `base_url`，HTTP API |
| **Agent 框架** | `app/`（仓库根目录，`core` + `harness`） | OpenAI 兼容对话 + 工具编排（隐式 ReAct）、FastAPI 接入与队列，示例 **`run_agent.py`** / **`run_agent_api.py`** |

设计细节见 **[register_center-设计.md](./register_center-设计.md)** 与 **[agent-framework-设计.md](./agent-framework-设计.md)**。

---

## 当前范围说明

**现阶段只实现：Agent 运行时 + Agent 间通信（发现、广播、点对点）及与之配套的轻量控制/编排能力。**

**暂不纳入本阶段：** Web 管理界面（列表、消息流可视化、图形化权限配置等）。权限与安全能力仍建议在消息层或控制平面以 **API/配置文件/策略存储** 形式落地，便于日后对接管理端。

---

## 1. 项目目标

构建一个**可动态编排的多 Agent 运行时**，支持：

- 按需定义与实例化多种类型的 Agent；
- 通过容器化实现**分布式部署**与水平扩展；
- 统一的**发现、广播与点对点通信**规则。

**后续扩展（非当前里程碑）：** 可视化管理界面（拓扑与状态、交互观测、访问权限的 UI 配置）。

---

## 2. 功能清单

### 2.1 第一部分：动态 Agent 与 Docker 分布式部署

| 编号 | 功能项 | 说明 |
|------|--------|------|
| A1 | Agent 类型抽象 | 定义 Agent 元数据（名称、能力标签、配置 Schema、入口命令等），支持注册多种实现（如 Python/Node 等）。 |
| A2 | 动态创建与生命周期 | 通过 API/CLI 创建、启动、停止、销毁 Agent 实例；实例带唯一 ID 与版本信息。 |
| A3 | 配置与密钥注入 | 支持环境变量、配置文件挂载、密钥引用（后续可对接 Vault/K8s Secret）。 |
| A4 | Docker 镜像规范 | 约定标准镜像结构、健康检查、日志输出格式，便于统一编排。 |
| A5 | 分布式部署 | 支持单机 `docker compose` 与多机 Swarm/K8s（或 Nomad）部署；节点可跨主机。 |
| A6 | 注册与编排对接（可选扩展） | 与现有容器平台集成：服务发现、扩缩容、滚动更新。 |

### 2.2 第二部分：Agent 间交互规则

| 编号 | 功能项 | 说明 |
|------|--------|------|
| B1 | 服务发现 | Agent 启动后向**发现层**注册；可查询当前在线 Agent 列表、能力、网络地址。 |
| B2 | 广播 | 支持主题/频道级广播（如 `topic`），订阅者接收；可限制速率与消息大小。 |
| B3 | 点对点通信 | 指定目标 Agent ID 发送请求/响应；可定义超时、重试与幂等约定。 |
| B4 | 消息格式与版本 | 统一信封（发送方、接收方、类型、载荷、追踪 ID）；向后兼容策略。 |
| B5 | 安全基线 | 传输层 TLS、可选 mTLS；消息签名或令牌校验；与权限策略（文件/API/DB）衔接。 |
| B6 | 观测与留痕（本阶段） | 结构化日志、可选消息采样落盘或写可观测 topic；**不要求** Web 展示，敏感数据注意脱敏。 |

### 2.3 后续扩展：管理界面（暂缓）

| 编号 | 功能项 | 说明 |
|------|--------|------|
| C1 | Agent 列表与拓扑 | 展示已发现 Agent、状态（在线/异常）、所属节点、能力标签。 |
| C2 | 交互信息流 | 实时或近实时展示选定时间范围内的消息流；支持按 Agent、主题、类型过滤。 |
| C3 | 访问权限矩阵 | 图形化定义「谁可以调用谁 / 谁可以订阅哪个主题」。 |
| C4 | 权限下发 | 策略变更后推送到运行时（或经中央策略服务校验每条消息）。 |
| C5 | 基础运维 | 查看日志片段、健康状态、简单告警（如连续心跳失败）。 |

## 3. 架构要点（建议方向）

以下为后续实现时的推荐拆分，可在详细设计中微调。

| 层次 | 职责 |
|------|------|
| **控制平面** | Agent 类型注册、实例创建指令、权限策略存储与下发（本阶段以 API/CLI/配置为主）。 |
| **数据/消息平面** | 发现注册表、消息总线（MQTT/NATS/Kafka + 适配层 或 自研轻量协议）、可选持久化。 |
| **Agent 运行时** | 各 Agent 进程内 SDK：注册、发广播、发 P2P、遵守权限。 |
| **管理 UI** | *暂缓*；日后可基于控制平面 API + 消息/事件订阅实现。 |

**发现与消息**：若希望快速落地，可采用 **NATS**（主题 + 请求-回复）或 **MQTT**；若强调顺序与回放，可引入 **Kafka** 作归档 topic。

**权限**：可在网关/消息中间件侧做 ACL，或在中央「策略服务」上对每条 RPC 做校验（延迟 vs 一致性权衡）。

## 4. 开发步骤与里程碑

建议按「先能跑通一条链，再补全运维与权限」的顺序推进。

### 阶段 0：仓库与约定（约 0.5～1 天）

- 仓库当前：`doc/` 设计文档；根目录 **`app/`** 为 Agent 代码；**`register_center/`** 为 Register Center 实现；管理端 Web UI 暂缓（前端见 [DAgentsUI](https://github.com/DGS-ai-team/DAgentsUI)）。
- 确定技术栈草案（后端语言、消息中间件）；前端框架待管理端立项后再定。
- 编写 Agent 镜像最小规范（目录结构、环境变量、健康检查路径）。

### 阶段 1：最小可用 Agent + 发现 + 单容器（约 1～2 周）

- 实现 **1 个示例 Agent**，启动后向发现服务注册并周期性心跳。
- 实现 **发现服务**（可先用内存或 Redis）。
- **Dockerfile + docker compose**：一键拉起发现服务 + 2 个示例 Agent。
- 验收：控制平面 API（或临时 CLI）能列出两个 Agent。

### 阶段 2：广播与点对点协议（约 1～2 周）

- 选定消息中间件并完成 SDK 封装（订阅广播、发送 P2P）。
- 定义 **消息信封** 与错误码。
- 第二个示例 Agent 演示：A 广播事件，B 订阅；C 向 D 发 RPC。
- 验收：自动化集成测试或脚本可重复验证。

### 阶段 3：权限模型与策略执行（约 1～2 周）

- 设计 **权限模型**（主体：Agent ID/类型；客体：目标 Agent / 主题；动作：publish/subscribe/rpc）。
- 实现策略存储与 **运行时校验**（入站消息拒绝时返回明确原因）。
- 验收：改策略后无需改镜像即可生效（或明确为「重启拉取」并文档化）。

### 阶段 4：生产化与分布式（持续迭代）

- 多节点部署文档（compose overlay / K8s Helm 草图）。
- mTLS、密钥轮换、资源限额。
- 访问与操作日志持久化与保留策略；控制平面 API 鉴权（API Key / JWT 等，按需）。

### 阶段 5（后续）：管理界面 MVP

- **列表页**：Agent 与状态。
- **交互视图**：消息流时间线（WebSocket/SSE）。
- **权限页**：矩阵或规则列表编辑保存。
- 验收：与阶段 2、3 的后端联调通过；可选管理端 OAuth2/OIDC。

## 5. 风险与依赖

| 项目 | 说明 |
|------|------|
| 消息中间件选型 | 影响延迟、运维复杂度与权限模型实现方式，宜在阶段 1 末拍板。 |
| 跨网络发现 | 多子网或 NAT 下需明确注册地址 advertised address，避免 Agent 广播错误 IP。 |
| 合规与隐私 | 交互日志可能含业务数据，需在存储与后续管理端做脱敏与访问控制。 |
