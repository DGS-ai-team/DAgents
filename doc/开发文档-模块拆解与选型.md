# 开发文档：功能模块拆解与技术选型（DAgents）

**版本**：0.1（面向落地）  
**范围**：基于 `doc/agent-设计.md` 中定义的能力，将系统拆解为可实现模块，并给出接口、配置、业务规则、技术选型与验收标准。  
**当前实现状态**：已完成主链路迁移为 OpenAI 原生 tool calling + 隐式 ReAct；本文其余模块（如 Register/MCP/多 Agent 调度）仍以规划为主。

---

## 1. 总体架构与模块边界

### 1.1 两层划分（核心逻辑 vs 周边设施）

- **核心 Agent 逻辑（core）**：OpenAI 隐式 ReAct 运行时、LLM 配置、Prompt/动态提示。
- **周边支持设施（harness + 外部服务）**：任务队列/并发闸门、消息接入、工具、记忆、脚本资产、MCP 动态工具、Register 协同、CLI/Frontend。

### 1.2 角色不是硬分类（配置组合）

终端/执行 Agent 通过配置组合得到：

- **可见性**：是否可被 Register/频道发现（discoverable）。
- **交互面**：是否开放 UI/CLI（interactive）。
- **调度策略**：是否接受其他 Agent 任务（accept_remote_tasks）。
- **能力暴露**：允许的工具集合（tools）、脚本目录、MCP 工具上限等。

9. **todo_list + 定时激活**：追加队列任务
10. **记忆压缩（规则化摘要）**

## 3. 模块设计（逻辑 + 业务细节 + 接口/配置 + 验收）

### 3.1 Agent 组装模块（core/main_agent）

**职责**
- 构造 OpenAI 隐式 ReAct 运行时：LLM 客户端、系统提示词、工具注册、会话状态与审批事件。

**落点（建议）**
- `app/core/main_agent/agent.py`：`init_agent()`
- `app/core/main_agent/runtime_openai.py`：`OpenAIImplicitReActRuntime`
- `app/core/main_agent/model.py`：`get_openai_client()` / `get_model_config()`
- `app/core/main_agent/prompt.py`：`get_system_prompt()`

**验收**
- 通过 API + CLI 全链路可完成：message -> (tool_call/interrupt) -> resume -> tool_result -> assistant -> done。

**实现备注（已落地）**
- `app/core/main_agent/agent.py`：`init_agent()` 返回 OpenAI runtime。
- `app/core/main_agent/runtime_openai.py`：实现隐式 ReAct 循环（OpenAI tool calling + 审批中断 + resume）。
- `app/core/main_agent/prompt.py`：`get_system_prompt()` 直接生成系统提示词（含当前 OS 类型）。
- `app/harness/tools/tool.py`：工具已通过 `openai_tools.py` 转换为 OpenAI tools schema。

---

### 3.2 运行入口与交互面（终端 Agent：CLI/Frontend）

**职责**
- 接收用户任务（CLI/Frontend）。
- 将任务拆解为子任务并调度执行 Agent（P1 起）。

**落点（建议）**
- CLI：`app/harness/cli/main.py`
- Frontend：`frontend/`（React 工程）
- Desktop 壳：`desktop/`（如 Tauri）

**业务细节**
- 终端 Agent 通常 `discoverable=false`、`accept_remote_tasks=false`。

**验收**
- CLI 可接受一次输入（后续可替换为 REPL 或子命令），并输出执行结果/计划。

**实现备注（已落地 / MVP）**
- `app/harness/cli/main.py`：仅保留 HTTP 方案二（`AGENT_CLI_MODE=api/http`），stdin -> FastAPI（`/v1/messages`）并消费 SSE。
- `run_agent_api.py` + `app/harness/api/app.py`：新增 FastAPI 接入层，统一接收客户端请求并转发到 `AgentService`。
- `run_agent_api.py` + `app/harness/api/app.py` + `app/harness/service/agent_service.py`：API 模式下由 FastAPI 生命周期托管 `AgentService`，按 `session_id` 维护队列并消费消息。
- `tests/test_agent_service.py`：已改为 runtime mock，验证统一事件信封映射与服务主流程。

### 3.3 任务队列与并发闸门（n 并发 + 排队）

**职责**
- 所有 Agent 维护任务队列。
- 同时最多处理 `max_concurrent_tasks=n`；超限排队（默认 FIFO）。

**接口（建议）**
- `enqueue(task)` → `task_id`
- `cancel(task_id)`（P1/P2 可做）
- `status(task_id)`（可选）

**配置（建议）**
- `MAX_CONCURRENT_TASKS`（默认 1 或 2）
- `MAX_QUEUE_SIZE`（可选，队列满时拒绝）
- `QUEUE_POLICY`（默认 FIFO，预留 priority）

**验收**
- 并发发起 \(n+K\) 个任务时，running ≤ n；多余任务进入 waiting。

**实现备注（已落地 / MVP）**
- 新增 `app/harness/queue/message_queue.py`：`MessageQueue` 基于 `asyncio.PriorityQueue`，优先级为 `human=0`、`resume=1`、`other=10`；消费者循环内对每条消息 **串行**处理。
- 当前入队接口为：`enqueue(envelope=..., priority=human|resume|other)`；`envelope` 由调用方构造（队列层不再构建 message envelope）。
- 支持运行态控制：`pause_consuming()` / `resume_consuming()` / `cancel_current()`。
- 配置落点：`app/config/settings.py` 暴露 `MAX_QUEUE_SIZE`（并同步到 `.env.example`）；并发上限参数暂未接入本模块。

### 3.4 工具体系 v0（bash 工具：分级名单）

**职责**
- 提供本地命令执行能力，但必须安全受控。

**业务规则**
- **语法校验**：拒绝明显非法命令串（空命令、奇异控制字符等）。
- **命令检测**：识别主命令（如 `git`/`python`/`ls`）。
- **名单分级**：
  - allow：可自主执行
  - ask：执行前必须询问用户确认
  - deny：禁止执行

**配置（建议）**
- `BASH_ALLOWLIST` / `BASH_ASKLIST` / `BASH_DENYLIST`（支持 glob/regex 的选型见 4.2）
- `BASH_TIMEOUT_SECONDS`
- `BASH_WORKING_DIRECTORY`（限定执行根目录）

**验收**
- deny 命令永不执行；ask 命令必须先走确认流程；allow 命令可直接执行并可回显 stdout/stderr。

**实现备注（已落地）**
- `app/harness/tools/bash.py`：`bash_run` 已可执行（bash/cmd/powershell），含分 shell 语句切分、黑白名单文件策略、超时与输出截断。

---

### 3.5 工具体系 v0（文件工具：read/write/edit）

**职责**
- 读取/写入/编辑本地文件，供 Agent 修改工程。

**业务规则**
- 默认只能访问工作区（防越权路径）。
- `edit_file` 优先使用“补丁式/片段式”编辑，避免整文件覆盖。
- 对二进制、超大文件有策略（拒绝或只读元信息）。

**配置（建议）**
- `FS_ROOT`（默认仓库根）
- `MAX_READ_BYTES`、`MAX_WRITE_BYTES`
- `ALLOW_EXTENSIONS`（可选：限制后缀）

**验收**
- 不能读到工作区外路径；对超限文件有明确报错。

**实现备注（已落地）**
- `app/harness/tools/fs.py`：`fs_read` / `fs_write` / `fs_edit` 已实现，含 FS_ROOT 越界保护、文本读取限制与 patch 编辑逻辑。

---

### 3.6 Register 协同（同频道发现）

**职责**
- 获取同频道（discovery_group/频道）内可用 Agent 清单。

**接口（建议）**
- `list_agents(channel)` → `[{agent_id, base_url, capabilities, ...}]`

**配置（建议）**
- `REGISTRY_URL`
- `DISCOVERY_GROUP`
- `DISCOVERABLE`（本 Agent 是否注册/可被列出）

**业务细节**
- 终端 Agent：`DISCOVERABLE=false`，不应出现在清单中。
- 执行 Agent：`DISCOVERABLE=true`，可被发现并接收任务（P1 起）。

**验收**
- 在同一 `DISCOVERY_GROUP` 下能拿到清单；不同组隔离。

---

### 3.7 多 Agent 调度（P2P + 广播）

**职责**
- 终端 Agent 将子任务分发给执行 Agent（定向或广播），回收部分结果并汇总。

**最小数据结构（建议）**
- `TaskEnvelope`: `{task_id, session_id, from_agent, to_agent|broadcast, payload, ttl, trace_id}`
- `TaskResult`: `{task_id, status, partial, artifacts, logs, error}`

**业务细节**
- 广播：多执行 Agent 返回“能完成的部分”，终端 Agent 负责合并与去重。
- 超时：必须有超时与降级策略（换 Agent、回退本地执行等）。

**验收**
- 可将一个拆分任务分别分配给 2 个执行 Agent，并合并输出（可先用本地 stub/模拟 Agent）。

---

### 3.8 MCP 工具：动态加载 + 最近使用保留 N

**职责**
- 支持将工具写成 MCP 服务并动态连接。
- 限制常驻工具数量（最近使用保留 N）。

**配置（建议）**
- `MCP_MAX_LOADED_TOOLS`（默认 5）
- `MCP_EVICT_POLICY`（默认 LRU）

**验收**
- 连续使用超过 N 个工具后，最旧工具被卸载/断开，不再占用常驻额度。

---

### 3.9 脚本资产系统（Python/SQL/CMD 等）

**职责**
- Agent 可生成脚本并落盘到特定目录。
- 通过 `list_python_script`（建议更名 `list_scripts`）先列“说明列表”，再选择读取/执行。
- 可按策略筛选说明列表以降低上下文占用（场景匹配、最近使用等）。

**目录与元数据（建议）**
- 目录：`app/harness/scripts/`（或仓库根 `scripts/`）
- 元数据：`<script>.meta.json`（字段建议：`id/name/description/tags/language/created_at/last_used_at/risk_level`）

**接口（建议）**
- `list_scripts(filter)` → `[{id,name,description,tags,language,last_used_at}]`
- `read_script(id)` → content
- `run_script(id, args)` → result（按语言选择执行器）

**验收**
- 列表默认只返回说明；读取脚本需二次选择；筛选策略生效。

---

### 3.10 记忆系统（开关 + 过期 + 压缩）

**职责**
- 按 `session_id` 维护历史消息。
- 支持 `MEMORY_ENABLED` 开关。
- 支持过期策略（TTL/上限）。
- 支持规则化压缩（摘要/窗口化/重要性保留）。

**配置（建议）**
- `MEMORY_ENABLED`（默认 true）
- `MEMORY_SESSION_TTL_SECONDS`
- `MEMORY_MAX_SESSIONS`
- `MEMORY_MAX_CHARS` / `MEMORY_MAX_TOKENS`
- `MEMORY_COMPRESSION_MODE`（off/window/summary/hybrid）

**验收**
- 关闭记忆后不再写入历史；超 TTL 自动清理；压缩规则触发后上下文明显缩短且仍保留关键信息。

---

### 3.11 todo_list + 定时激活

**职责**
- Agent 维护 `todo_list`；按固定间隔触发处理。
- 定时器本质：向任务队列追加“处理 todo”任务。

**配置（建议）**
- `TODO_ENABLED`
- `TODO_TICK_SECONDS`
- `TODO_MAX_PER_TICK`

**验收**
- 到达 tick 后会生成任务进入队列；MVP 下队列消费为串行，多并发处理待后续与并发闸门对齐。

## 4. 技术选型（推荐 + 备选）

### 4.1 语言与运行时

- **推荐**：Python 3.11+（当前仓库已是 Python）。
- **并发**：`asyncio` + `anyio`（如后续接 Web 服务/队列）。

### 4.2 Register Client / HTTP

（当前仓库未包含 Register 实现目录，文档接口见 `doc/register-center-设计.md`）

- **推荐**：`httpx`（异步/同步皆可）
- **备选**：`requests`（简单但不适合 async 全链路）

### 4.3 队列与定时

- **进程内 MVP**：`asyncio.Queue`（当前实现为串行消费）；并发闸门可用 `asyncio.Semaphore`/多 worker（后续）
- **跨进程/分布式（后续）**：Redis（RQ/Arq/Celery）或 NATS/Kafka（更重）

### 4.4 脚本执行器

- Python：`subprocess`（隔离进程）或 in-proc（不推荐，风险大）
- SQL：优先“生成 + 人工确认”模式；若执行需绑定具体数据库驱动与权限（另文）
- CMD/shell：走同一 bash 工具通道，复用分级名单与审计

### 4.5 安全基线（必须做）

- 工作区路径限制（FS_ROOT）
- bash 命令分级名单 + 超时 + 禁止高危命令
- 动态工具/MCP 连接上限与来源约束
- 审计日志（至少：谁触发、执行了什么、结果、耗时）

### 6.4 已知限制（发布说明建议写明）

- OpenAI tool calling 依赖模型输出工具参数；需持续优化参数校验与高危命令策略。
- `AgentService` 目前按 `session_id` 维护最多 3 个活跃队列，超限会拒绝新会话。
- 队列消费为串行（每个 session 单消费者），并发执行策略后续再扩展。
- 事件总线当前为进程内内存实现，服务重启后不保留历史流事件。
